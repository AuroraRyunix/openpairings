# Whole-codebase audit, 2026-09-05

An adversarial read of the whole codebase, run as a swarm of short-lived
verifier agents over fourteen dimensions, then a second pass over six named
gap areas the first pass had not owned. Ninety-six raw findings went in;
**43 were confirmed** and 53 were refuted or left unjudged. Severity split:
1 critical, 13 high, 15 medium, 14 low.

Three documents, three jobs, same as the sweeps: [TODO.md](../TODO.md) is
the roadmap, this is the evidence, and the fixes are in the CHANGELOG under
the versions named below.

## Why this document exists, and what is weak about it

The audit finished on 2026-09-05 and **was never written into the
repository**. For three days its findings lived in one assistant memory
note and a session transcript, which is not a place work can be picked up
from. It was reconstructed and filed on 2026-09-08.

The reconstruction is stronger than that history suggests, and it is worth
knowing exactly how strong, because the parts differ:

- **The 43 confirmed findings are high-confidence.** The audit session had
  written their full text - file, line, mechanism - to a working file that
  survived intact. The content below is that text, not a summary of a
  summary.
- **Every status below was re-derived from code, not from narration.** On
  2026-09-08 each finding was checked against the then-current HEAD of all
  four repositories by reading the actual source. Where the transcript's
  own account and the code disagreed about whether something had been
  fixed, the code won. One case of that is recorded at finding 12.
- **The refuted findings are lost.** Fifty-three findings were refuted or
  unjudged, and their individual titles and reasoning are not recoverable -
  the verifier subagents' transcripts were ephemeral and the audit session
  knew it, consolidating only the confirmed set before they aged out. Only
  the counts survive. This is the real cost of not writing an audit down
  while it is running: **the same thirty refuted findings can be found
  again, argued again, and refuted again by the next pass**, at full price.

That last point is the lesson, not the inconvenience. The two earlier
sweeps ([2026-08-26](sweep-2026-08-26.md),
[2026-09-01](sweep-2026-09-01.md)) both kept a "Refuted, and kept here on
purpose" section for exactly this reason. This audit did not, and the
information is gone.

## High

### 12. Every `Tools.Session` write copies the whole upload store into the writer's heap

`lib/pairings_engine/tools/session.ex` - `total_bytes/0` (~161),
`enforce_cap/0` (~146)

`total_bytes/0` calls `:ets.foldl` and `enforce_cap/0` calls
`:ets.tab2list()` over the entire table on **every write**, which is an
O(bytes currently stored) copy into the calling process's own heap for a
single put. Any anonymous visitor to `/tools/norms` reaches it.

Note the near-miss: `877926a` (2026-09-08) added a per-address rate limit to
that page, 60 files per 10 minutes, and it is easy to read that as having
closed this. It did not - its diff touches `rate_limit.ex` and
`tools_norms_live.ex` and never `session.ex`. A per-IP limiter bounds how
fast *one* address adds load; the finding's own text is about N connections
holding N such copies at once, which a per-IP limit does not address. The
rate limit was the cheapest hardening of that surface, not a fix for this.

**Fixed** in 0.52.0. Both reads are now an `:ets.select` with the stored
upload left out of the result, so a write walks one small tuple per entry
instead of copying every entry's contents. The budget's arithmetic and its
eviction order are untouched; only the copying is gone.

### 14. Login tokens are written to the production log while still valid

`lib/pairings_engine_web/endpoint.ex:63`

`plug Plug.Telemetry, event_prefix: [:phoenix, :endpoint]` carries no `:log`
option, so Phoenix logs the full request path at `:info` in production -
including `GET /users/log-in/<token>` and the other routes that carry a
bearer token in the path (confirm-email, invites, tools download, mobile
enrol). The magic-link token stays live for fifteen minutes after it lands
in the log.

Nothing has touched this line since. It was listed under Security in the
audit's own summary alongside the critical and finding 43; only the
critical was acted on that day.

**Fixed** in 0.52.0. `PairingsEngineWeb.Plugs.RequestLogging` logs those
five paths with the secret segment replaced (`GET /users/log-in/[FILTERED]`)
and tells Phoenix's own handler to skip the line it would have written for
them. Every other request is logged exactly as before - going quiet on five
routes would have traded a leak for a blind spot.

## Medium

### 19. One unindexed scan of the 1.9M-row FIDE table per country in an uploaded `.swar`

`lib/pairings_engine/federations/bel/swar_import.ex` -
`build_fide_candidates_cache/1` (~800)

One `Repo.all(from f in FidePlayer, where: f.federation == ^federation)` per
distinct normalised country string in the uploaded file, against an
unindexed column. A file naming ~39,000 distinct country strings buys
39,000 sequential full scans of a 1.9M-row table, all before a single row is
written.

**Fixed** in 0.52.0. One `in` query covering every federation the file
names, chunked well under SQLite's bound-parameter limit, and an index on
`fide_players.federation` behind it.

### 20. `accept_pending` broadcasts from inside its own uncommitted transaction

`lib/pairings_engine/registrations.ex` - `accept_pending/2` (~328)

`Tournaments.create_player/2`, called inside the `Repo.transaction`,
broadcasts before the transaction commits with two statements still to run.
Under WAL a subscriber can re-query and render a roster that does not
contain the player just accepted. This is the one broadcasting transaction
in the codebase that does not use `with_broadcast_suppressed/1`.

**Fixed** in 0.52.0. `with_broadcast_suppressed/1` around the transaction
and one broadcast after it, the same shape the four other bulk writes use.

### 21. `ResultsImport.parse_text/1` raises, and its moduledoc promises it never does

`lib/pairings_engine/results_import.ex` - `maybe_drop_header/2`,
`parse_line/3`

`Integer.parse/1` on the CSV's first field has no length guard, so a
1.3-million-digit board number raises `SystemLimitError` and kills the
arbiter's `PairingsLive` process mid-round. The module's own moduledoc says
"Never raises."

The 09-08 fix to the same file bounded the accumulated *error list*, a
different code path; it did not incidentally close this.

**Fixed** in 0.52.0. The board field's length is checked before
`Integer.parse/1` is handed it, so a field no board number could occupy is
refused as one instead of being converted first.

### 25. TRF field `122` is exported from one field and imported into another

`lib/pairings_engine/trf_import.ex:434` vs
`lib/pairings_engine/trf_export.ex:205`

The export writes `122` from `tournament.rate_of_play`; the import writes
the parsed value into `tournament.time_control`. An export-import round trip
therefore empties `rate_of_play` - the setup checklist then reports "Rate of
play" as missing - and a second export emits no `122` line at all.

Worth noting because it is the kind of thing that looks fixed: the TRF26
work of 09-07 and 09-08 (`075cb29`, `2e41c0e`, `425fa09`) rewrote a great
deal of the machinery on both sides of this line and did not touch this
mapping.

**Fixed** in 0.52.0, on the import side: `122` is "allotted times per
moves/game", which is `rate_of_play` - the field the Options page edits, the
checklist looks for, the norms forms read and the export writes that line
from. `time_control` stays what it has been since that field replaced it: a
fallback for tournaments that predate it, editable on no page.

### 26. The projector view crashes when its round stops being published

`lib/pairings_engine_web/live/live_round_live.ex` - `page_count_for/1`
(~109) against the `round:` assign in `reload/1` (~362)

The assign is `round: shown > 0 && Tournaments.get_round(...)`, which
evaluates to the atom `false` - not `nil` - when nothing is published.
`page_count_for(%{round: nil})` never matches `false`, so it falls through
and raises `BadMapError` on `round.pairings`.

Finding 39 is the same false-versus-nil root cause in another branch of the
same LiveView. A third instance is finding 41. The sibling finding 27 in
this same file *was* fixed on audit day (`75983e3`); these were not.

**Fixed** in 0.52.0 at the assign rather than at its readers - `if` in
place of `&&`, so the value is `nil` when nothing is published, which is
also what `get_round/2` answers for a round that is not there. That is one
line for this and for finding 39.

### 29. `MemoryLow=768M` is inert, because nothing protects `system.slice`

`openpairings-deploy/deploy_openpairings.py` (~1500)

`memory.low` is hierarchical in cgroup v2. The script's only
`systemctl set-property` call targets `user.slice`, and
`pairingsengine.service` lives in `system.slice`, whose effective
`memory.low` therefore stays 0. The documented soft floor never engages
under memory pressure - which is the only condition it exists for.

**Fixed** 2026-09-09 in the deploy script. `system.slice` is given its own
`MemoryLow` before the units are written, so the figure in the unit is no
longer clamped to zero by its parent.



## Low

### 30. `WeightedMatching.new/3` builds a phantom vertex `-1` at n = 0

**Ainalrami** - `lib/ainalrami/weighted_matching.ex:858`, `:865`

`Map.new(0..(n - 1), &{&1, &1})` with no `//1` step. At `n = 0`, `0..-1` is
a descending range in Elixir's two-argument form, so it enumerates
`[0, -1]` and injects a bogus `-1 => -1` into both `:in_blossom` and
`:base`, with a deprecation warning. Reachable through
`Pairing.pair_next_round([], forbidden_pairs: [...])`.

No wrong pairing comes of it - the answer is empty either way. Other ranges
in the same file (~942, ~959, ~964) already carry `//1`; these two were
missed.

**Fixed** in Ainalrami v0.25.0. Both ranges carry `//1`, with a test that
the `n = 0` path produces no `-1` entry.



### 33. The page-cache ETag is an unkeyed hash, and can be collided on purpose

**OpenResults** - `lib/openresults_web/plugs/revalidate.ex:108`,
`etag_for/2`

`:erlang.phash2({request_path, query_string})` - public, deterministic,
unkeyed, and a 2^27 range. A colliding query string for a target page can be
computed in seconds, which serves one page's rendered body under the URL a
legitimate reader uses. It cannot cross tournaments and cannot surface a 404
or a withheld page: this is confusion and defacement, not disclosure.

Adjacent but separate from the page-cache eviction bug fixed in `7919ec7` on
2026-09-08. That commit restructured `page.ex`'s keys and never touched
`revalidate.ex`.

**Fixed** 2026-09-09 in OpenResults. The tag is an HMAC keyed with 32 random
bytes drawn once per boot: stable for the life of a snapshot, so it still
works as an HTTP validator, and not computable by anyone without the secret.



### 34. Backup's `@fts_tables` never learned about `kbsb_players_fts`

`lib/pairings_engine/backup.ex:81`

The constant lists `fide_players_fts` only - `kbsb_players_fts` arrived a
day after it was written. So every backup ships that index intact instead of
stripping it, and a restore leaves `kbsb_players` empty while
`kbsb_players_fts` still holds ~36k rows, which breaks
`Members.fts_search/1`. Self-repairing: the next KBSB sync drops and
rebuilds both.

**Fixed** in 0.52.0.

### 35. KBSB search leaves a double quote in its FTS5 tokens

`lib/pairings_engine/federations/bel/members.ex:86` - `search_tokens/1`

Strips `%` and `_` but not `"`, so a query like `a"b` breaks out of the
quoted FTS5 term - either a syntax error, which falls back to a full `LIKE`
scan of ~36k rows on every keystroke, or a valid-but-different query
carrying an unintended column filter. Not injection: the MATCH string is a
bound parameter. Both sibling implementations (`Fide.search_tokens/1`,
`SwarImport.fide_players_matching_tokens/1`) already strip the quote.

**Fixed** in 0.52.0.

### 36. `SwarUpload`'s moduledoc describes the opposite of what the code does

`lib/pairings_engine/federations/bel/swar_upload.ex:39`

The moduledoc still says the GUID braces pass through unencoded by raw
string concatenation. They have been percent-encoded through `URI.encode/2`
since an earlier fix, which has its own inline comment explaining why. No
runtime effect - the risk is a maintainer trusting the doc as the spec and
"restoring" the broken behaviour.

**Fixed** in 0.52.0. The moduledoc now describes the encoding the code
actually performs and why a conforming client cannot do otherwise; the stale
half of `do_index/1`'s own comment, which contradicted the line under it,
is gone with it.

### 37. An imported `.swar` GUID reaches a `Content-Disposition` header unvalidated

`lib/pairings_engine_web/controllers/export_controller.ex` - `swar_html/2`
(~185); `lib/pairings_engine/tournaments/tournament.ex` - the `:swar_guid`
cast

No `validate_format` on the cast, and `SwarPublish.filename/1` puts the
value straight into the header. A control character in the GUID makes that
tournament's SWAR HTML download 500 forever, because Plug rejects the
header; a quote breaks out of the quoted filename parameter. Low because it
is self-inflicted and single-tenant.

**Fixed** in 0.52.0. The cast refuses quotes, slashes and control
characters - the characters that break a header - rather than asserting a
shape for a value another program mints.

### 39. The "no round has been paired yet" card is unreachable

`lib/pairings_engine_web/live/live_round_live.ex:689`

Guarded on `@round == nil and @paired_rounds == 0`, and the assign is
`false`, never `nil`. A brand-new tournament's Local view therefore shows
nothing at all where the explanation should be. Same root cause as 26 and
41.

**Fixed** in 0.52.0, by the same line as finding 26.

### 40. A handed-off tournament leaves the phone's result buttons enabled

`lib/pairings_engine_web/live/mobile_results_live.ex:86`, `:139`

`archived?` is derived from `tournament.archived_at` alone and never
consults `handed_off_at`, so the buttons render enabled. The write is
correctly refused server-side with `{:error, :handed_off}` - but that error
has no matching clause and falls through to the generic "Could not save that
result." The access control is sound; the explanation is missing, on a
phone, mid-round.

**Fixed** in 0.52.0. The buttons follow `Tournaments.ensure_writable/1`,
the gate every write in the app is refused by, instead of re-reading one of
its two reasons - and `{:error, :handed_off}` has a clause of its own, worded
like its archived sibling.

### 41. `force_unlock_confirmed` crashes the LiveView with no return target staged

`lib/pairings_engine_web/live/tournaments_live.ex:325` (handler), `:83`
(assign), `lib/pairings_engine/tournaments.ex:1543` (`force_take_back/2`)

`return_target` is `nil` at mount and set only by `return_start` or a
`return` param. `force_take_back/2` has one clause, matching
`%Tournament{}`, so firing the event from a freshly loaded page raises
`FunctionClauseError` and kills the LiveView. `delete_confirmed` and
`purge_confirmed` pattern-match defensively here; this one does not.

**Fixed** in 0.52.0. Matched defensively like the two siblings named
above, and the word an arbiter has to type is now required by the server
rather than only by the button's `disabled`.

### 43. A permanent `gpgcheck=0` repository, and an unverified zip unpacked as root

`openpairings-deploy/deploy_openpairings.py` (~1611, ~1633)

When `erl` is missing the script writes a permanent
`/etc/yum.repos.d/rabbitmq-erlang.repo` with `gpgcheck=0` and `enabled=1`
and never disables it again, so **every later `dnf update` on that box
installs unsigned packages from it, indefinitely**. Separately, an Elixir
release zip is curled from GitHub and `unzip -o`'d into `/usr/local` as root
with no checksum and no signature check.

A one-time provisioning path, which is why it is not higher - but its first
half is permanent once taken.

**Fixed** 2026-09-09 in the deploy script. The repository is signed against
RabbitMQ's published Erlang key and left `enabled=0`, with `--enablerepo` on
the single install that needs it, so no later `dnf update` reaches it. The
Elixir archive is checked against the `.sha256sum` published beside it and
nothing is unpacked on a mismatch - verified both ways, the real archive
passing and a one-byte-altered copy refused.

## One finding was never judged

"The public officials form re-serialises the whole session on every
keystroke", medium. Its reviewer was blocked twice by a safety classifier
and the final pass returned a single verifier vote, below the quorum needed
to count it either way. It is not one of the 43, and it was also never
cleared. Left here so it is neither counted nor lost.

**Judged on 2026-09-13, and it was two different pages.** "Public" reads
two ways, and both turned out to matter - one already fixed, one still
open:

- **The signed-in Norms page** (`lib/pairings_engine_web/live/norms_live.ex`,
  `phx-change="officials_change"`) is where "public" would mean "feeds a
  FIDE-facing report." This was true before 2026-09-02 - the roster sort and
  the IT3 counts ran inline in the template, so any re-render, on any event,
  recomputed both over every player - but two commits three days *before*
  this audit ran fixed it: `632d77a` memoised both into assigns computed
  once per roster load, and `319b0e8` added `phx-debounce="300"` to the
  whole form and reduced `officials_change` itself to `assign(socket,
  dirty: true)` - an assign the template never reads. The blocked,
  under-quorum review was very likely looking at code that had just changed
  out from under it.

  Verified against the current code, not just re-read: a 200-player
  tournament's `officials_change` costs the same **397 VM reductions**
  (Erlang's own CPU-work counter, immune to wall-clock jitter) as a 5-player
  one - flat, not scaling - touches zero database queries, and broadcasts
  nothing. `test/pairings_engine_web/live/norms_officials_test.exs` already
  traced that the roster-sort function is never called from this handler;
  a new test in the same file additionally pins the query count and the
  broadcast silence. **No code change; already fixed pre-audit.**

- **The actual public, no-login page**, `/tools/norms`
  (`lib/pairings_engine_web/live/tools_norms_live.ex`), is where "public"
  means "reachable without an account" - and "session" is not a figure of
  speech, it's `PairingsEngine.Tools.Session`, the in-memory store backing
  that page (see finding 12). Its "Officials & arbiter candidate" card
  (`phx-change="update_fields"`) carries **no `phx-debounce` anywhere on the
  page**, and every keystroke calls `sync_session/1`, which calls
  `Session.put/2,3` on the *entire* session payload - every file uploaded
  so far, parsed tournament and full player list included - not just the
  small overlay/candidate map that changed. `Session.put/3` computes
  `:erlang.external_size/1` over that whole payload and `:ets.insert/2`
  deep-copies it into the shared table; both are genuinely whole-term
  operations, confirmed to cost **linearly in the total uploaded data**,
  roughly 750-880 bytes/microsecond measured from empty up to 4.6 MB:

  | uploaded players | payload size | `Session.put/2`, averaged |
  |---:|---:|---:|
  | 0 | 608 B | 10.2 µs |
  | 100 | 22.6 KB | 30.7 µs |
  | 1,000 | 228 KB | 261.1 µs |
  | 5,000 | 1.1 MB | 1.30 ms |
  | 20,000 | 4.6 MB | 5.91 ms |

  At the sizes this page sees in practice (hundreds to a couple of thousand
  players across the uploaded file(s)) that's tens to a few hundred
  microseconds - not perceptible to a typist. Near the page's own ceiling
  (ten files at the 5 MB/file cap) the same arithmetic reaches the tens of
  milliseconds per keystroke, uncollapsed by any debounce, on a page that is
  unauthenticated and - unlike the file-parsing step, rate-limited since
  `877926a` - not throttled on this path at all.

  **Fixed in `1ab5361`.** Both halves of the follow-up this finding asked
  for: the officials form carries the same 300ms `phx-debounce` the
  signed-in Norms page's already has, and `update_fields` and its siblings
  (`arbiter_pick`, `add_arbiter`, `remove_last_arbiter`, `pick_candidate`)
  now sync only the small overlay/candidate maps, through a new
  `Session.put_patch/2` that upserts a companion entry rather than replacing
  the whole one - `Session.get/1` shallow-merges it back on for every reader
  (the download route included), so a reload or reconnect restores exactly
  what it restored before, and nothing here changed what `sync_session/1`
  itself writes when a file is actually added or removed. Measured the same
  way, on the same shape of upload (a real parsed 5,000-player file, 5.48 MB
  session payload, averaged over 200 calls): re-syncing the whole session on
  a field edit cost **~7.5 ms**; syncing the patch alone costs **~8.5 µs** -
  about **880x less**, and no longer proportional to what has been
  uploaded.
