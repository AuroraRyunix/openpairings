# Codebase sweep, 2026-08-26

A deliberate read of the whole of OpenPairings looking for bugs,
optimizations and things worth adding - not a response to a bug report.
Ten broad-scope readers across the two repositories, and then **every
bug-severity claim handed to a second reader whose only job was to refute
it**, told to default to "not real" when uncertain.

Across both repositories: **18 claims survived, 3 were refuted.** The
refuted ones are kept below rather than deleted, because a good refutation
is the more useful document - it explains why something that looks obviously
broken is deliberate.

Most of the bug-severity half has since been fixed. The tally, and the
commit for each finding, is in **Status** directly below; the rest of the
document is left as it was written, so a finding's own text still describes
the code as it was on the day. The Ainalrami half is in that repo's
`docs/sweep-2026-08-26.md`.

**Lead #1 - `classify_result` catch-all, keizer.ex:605.**
For: the blank state is real and this module creates it - keizer.ex:414
inserts every fresh pairing with `result: ""` - and `_ -> :zero`
(keizer.ex:605) sends it to a `round_stats/2` bucket that increments
`played` and `losses` (keizer.ex:266-271). `Standings.pairing_records/4`
answers `[]` for the same state, so the two implementations disagree.
(The body of this document, and `tournaments.ex:2172`, call it
`pairing_records/3`. It is arity 4 - `pairing, round_number, t, presence?`
at standings.ex:419. That mislabel is inherited, like #11's `fill_seat/4`.)
Against: `score_all/5`'s own `@doc` (keizer.ex:511) defines `:zero` as
"played `0-0` **or otherwise unaccounted**", which documents the catch-all
rather than leaving it accidental, and `class_points(:zero, ...)` is 0.0, so
the ladder - the only thing Keizer scoring exists to produce - is right. The
wrong columns are display-only and correct themselves as results arrive.

> **CONFIRMED as a code defect; the claimed harm is REFUTED.** The blank
> result genuinely reaches `_ -> :zero` and is genuinely counted as a
> played loss, with no guard and no test - `keizer_test.exs:47`'s
> `@every_result` claims to drive "every result string the app can store"
> and omits `""`, the one this module writes on every pairing. But
> `played`, `wins`, `draws` and `losses` are DEAD FIELDS: `Keizer.standings/2`
> returns them and nothing in `lib/` or `test/` reads them. All four Keizer
> surfaces render Score only. The single live consequence is `raw_points`
> inflated by `points_loss` per unreported game - zero by default, so
> visible only where an arbiter has set a non-zero loss value.
> **Fix:** a `{"", _} -> :not_played` clause ahead of the catch-all, with a
> `round_stats/2` bucket that increments nothing, mirroring
> `Standings.pairing_records/4`. Add `""` to `@every_result`.

**Lead #6 - `adjusted_score/3`, standings.ex:770.**

## What the sweep was aimed at

One shape above all: **the same rule written down twice, where the copies
drift apart silently.** That is the shape behind every real bug found in
0.17.1 - a played-code list that lost `W`/`D`/`L`, a bye scored from its TRF
letter instead of its kind, an options list written out twice - and it is
the shape unit tests are worst at catching, because both copies are
individually consistent.

It found more of them. Two of the confirmed bugs are the *same* `W`/`D`/`L`
vocabulary missed in two further private copies, and one is a result
vocabulary that grew in one consumer and not the other in the same module.

## The four worth reading first

1. **A TRF this app exported cannot be re-imported without data loss.**
   `TrfImport` keeps a private `@playing_codes` that never gained
   `W`/`D`/`L`, so every unrated played game fails to resolve to a mutual
   pairing and is reinterpreted as a **bye** - the opponent is lost. The
   proof it was meant to work sits three lines below:
   `result_string("W", _) -> "1-0U"` is unreachable dead code.
2. **Two players can end up sharing a pairing number.**
   `ensure_pairing_numbers/2` takes its "highest number so far" over the
   *active* subset, so marking the top-numbered player absent and then
   registering a walk-in hands the newcomer a number already in use. Nothing
   rejects it - no unique index, no changeset check - and the exported FIDE
   TRF then carries two rows with the same starting rank.
3. **Keizer standings crash** (`CaseClauseError`) the moment an asymmetric
   `1/2-0` result is entered. `classify_result/2` emits `:half_win` and
   `:half_loss`; `round_stats/2` - the other consumer of that vocabulary, in
   the same module - lists nine classes, neither of those, and has no
   catch-all.
4. **`pair_from_pool/4` and `fill_seat/4` seat a player id that is never
   checked against the tournament.** A scope hole in the manual-pairing
   path.

## A correction to an earlier draft of this document

An earlier version headlined a fourth bug: that `@round_fields` omits
`Round.explanation`, so JSON backup and snapshot restore destroy every
round's pairing rationale. **The refutation pass killed it, and it was
right.** The explanation blob stores database *player ids*, and both import
and restore delete and re-insert every player with fresh ids while remapping
only the references they know about - not the ones nested inside that blob.
Exporting the field as proposed would restore an account full of dead ids,
render blank names, and make `divergence/1` show the red "the boards have
changed since this was recorded" banner on every restored round, which would
be a lie. The current nil is the safe outcome.

What survives is a smell, not a bug: the exclusion is undocumented, and
nothing pins the round field list the way `tournament_export_test.exs` pins
the tournament one. It is filed below as such.

### ensure_pairing_numbers/2 takes max_existing over the ACTIVE subset, so a new player can be handed a pairing_number already held by an absent/withdrawn one

`lib/pairings_engine/pairing.ex:263`

> **Verified**, confidence high.

The docstring (pairing.ex:251) says numbers continue "from the current max existing number", but the code takes the max over the `players` list it was handed, and BOTH callers hand it the active-only subset: `Pairing.pair_next_round/1` (pairing.ex:104,120) and `Keizer.do_pair/4` (keizer.ex:126) both pass `active_players/1`, which excludes `status != "active"`, `absent == true` and `forfeit == true`. Any of those three flags on the highest-numbered player removes their number from the max computation while the number itself stays frozen on the row. There is no unique index and no changeset validation on `pairing_number` (priv/repo/migrations/20260709183000_add_pairing_number.exs:8 adds a plain `:integer`; Player.changeset at lib/pairings_engine/tournaments/player.ex:80-113 has no uniqueness check), so the duplicate is written without complaint. `guard_pairing_number_freeze/2` (tournaments.ex:1322) only guards CHANGING an existing number and explicitly permits nil -> N.

The module already has the right set for this question: `full_roster_players/1` (pairing.ex:1895) and `build_shared_history/1` (pairing.ex:2073) both define "every player who ever received a pairing_number" precisely because a rank question must not be scoped to the currently-eligible pool. `max_existing` is the one place that rule is written a second time, over the wrong set.

Blast radius: the live pairing run survives (do_pair_single remaps to a local contiguous 1..M map), but PairingsEngine.TrfExport emits `trf_player_rows/3` rows with the RAW `pairing_number` as `:rank` (pairing.ex:1752), so the downloadable FIDE TRF carries two rows with the same starting rank. Worse, `Trf.validate_games!/2` builds `by_rank = Map.new(players, &{&1[:rank], &1})` (trf.ex:493), which silently collapses the two, so `validate_playing_pair!/5` cross-checks games against the wrong player and can raise a bogus `Trf.ValidationError` that kills the download outright. `order_for_pairing/3` also uses `pairing_number` as its final tie-break (pairing.ex:1885) — the tie-break whose own comment says it exists so the order is reproducible — and two players sharing it puts that back to `Enum.sort_by` stability.

**Evidence.** pairing.ex:260-268
  def ensure_pairing_numbers(tournament, players) do
    if Enum.any?(players, &is_nil(&1.pairing_number)) do
      max_existing =
        players |> Enum.map(&(&1.pairing_number || 0)) |> Enum.max(fn -> 0 end)

      players
      |> Enum.filter(&is_nil(&1.pairing_number))
      |> Enum.sort_by(&{-Player.rating(&1), &1.name})
      |> Enum.with_index(max_existing + 1)

pairing.ex:104,120 (caller)
    active = active_players(tournament.id)
    ...
          |> ensure_pairing_numbers(active)

pairing.ex:1913-1919 (what that set excludes)
  def active_players(tournament_id) do
    Repo.all(
      from p in Player,
        where:
          p.tournament_id == ^tournament_id and p.status == "active" and
            p.absent == false and p.forfeit == false

CONCRETE INPUT: 10-player Swiss, round 1 paired -> numbers 1..10 frozen. The lowest-rated player (number 10) then requests a full-tournament bye, so the arbiter ticks Absent (`absent: true`, the Pr. column menu, or `set_all_players_absent/2`). A walk-in registers before round 2. Pairing round 2: `active_players/1` returns numbers 1..9 plus the newcomer (nil); `max_existing = 9`; the newcomer is written `pairing_number: 10`. Two players now hold rank 10 for the rest of the event.

**Fix.** Compute `max_existing` from the tournament's whole frozen roster, not from the passed-in list — e.g. `Repo.one(from p in Player, where: p.tournament_id == ^tournament.id, select: max(p.pairing_number)) || 0`, which is the same set `full_roster_players/1` already defines. A unique index on `(tournament_id, pairing_number)` would make the invariant enforceable rather than merely intended.

**What the refutation pass found.** CONFIRMED (core defect real; one secondary consequence overstated).

Mechanism verified end to end:
1. lib/pairings_engine/pairing.ex:260-275 - `max_existing` is `Enum.max` over the `players` argument only.
2. Both callers hand it the active-only subset: pairing.ex:104/120 (`active = active_players(tournament.id)` then `ensure_pairing_numbers(tournament, active)`) and keizer.ex:126 (`Engine.ensure_pairing_numbers(tournament, Engine.active_players(tournament.id))`).
3. pairing.ex:1913-1920 - `active_players/1` filters `status == "active" and absent == false and forfeit == false`, so any of those three flags on the highest-numbered player removes their number from the max while the number stays on the row (nothing nils it; `guard_pairing_number_freeze/2` at tournaments.ex:1322-1344 only guards changing an existing number and explicitly permits nil -> N).
4. Nothing rejects the duplicate: priv/repo/migrations/20260709183000_add_pairing_number.exs:8 adds a plain `:integer` (the only unique indexes in priv/repo/migrations are tournament+fide_id and forbidden_pairings), and Player.changeset (lib/pairings_engine/tournaments/player.ex:75-113) casts `:pairing_number` with no uniqueness/constraint check.
5. Reachability holds: numbers are only assigned to players who were active AT assignment time, so the max-holder becomes non-active only later - exactly the claimed sequence. The arbiter can set `absent` mid-event from the players grid (players_live.ex:531 `Tournaments.update_player(player, %{"absent" => absent?})`), and a UI-created walk-in has `pairing_number: nil` (only SwarImport/TrfImport set it at creation).

WHY THIS IS NOT THE BUG AS CLAIMED
1. The claim's repro asserts "the field would round-trip for free if it were exported". 2. This puts `explanation` in exactly the class of exclusion the file *does* document three lines below it — `pairing_map/1`'s `match_id` comment (tournament_export.ex:149-155): an id that would dangle or point at the wrong row after remapping, so it is not carried.

### Standings tiebreaks are O(N²R²): a whole-field scan runs inside the per-game inner loop, and adjusted_score is never memoized

`lib/pairings_engine/standings.ex:695`

`adjusted_score/3` is the inner loop of every Buchholz-family and SB tiebreak, and it opens by recomputing a value that is constant for the entire standings run:

```elixir
# standings.ex:693
defp adjusted_score(opp_entry, by_id, t) do
  games = Enum.sort_by(opp_entry.games, & &1.round)
  total_known_rounds = rounds_played_count(by_id)   # <-- line 695
```

```elixir
# standings.ex:787
defp rounds_played_count(by_id) do
  by_id |> Map.values() |> Enum.map(&length(&1.games)) |> Enum.max(fn -> 0 end)
end
```

`by_id` is built once in `compute_tiebreaks/3` (line 561) and never mutated, so `rounds_played_count(by_id)` returns the same number every time — but it walks all N entries and calls `length/1` on each R-element game list on every call, i.e. O(N·R) per call.

Call count: `buchholz_contributions/3` (line 678) calls `adjusted_score` once per game, and is itself called separately for BH, BHC1, BHC2 and MBH (lines 591-593) with no memoization; `tiebreak("SB", ...)` (line 596) calls `adjusted_score` per game again. `adjusted_score` is also recomputed from scratch for the same opponent every time a different player faced them, even though only N distinct answers exist. `tiebreak("KS", ...)` at line 635 calls `rounds_played_count(by_id)` once per entry as well.

Net: O(N²R²) per standings computation. Nothing is cached — I checked for ETS/persistent_term/Cachex and the only ETS tables in the app are rate limiters and the tools session store.

This is not a cold path. `PlayersLive.assign_players/1` calls `Standings.grid_standings/1` (players_live.ex:167), which forces `~w(BH BHC1 SB PS DE)` on top of the tournament's configured codes (standings.ex:54) — so at least three adjusted-score passes run regardless of configuration. `assign_players/1` runs on mount AND on every `{:tournament_changed, ...}` broadcast (players_live.ex:139-159), in every connected PlayersLive process, i.e. every time any arbiter enters any result.

**Evidence.** standings.ex:695 `total_known_rounds = rounds_played_count(by_id)` inside `adjusted_score/3`; standings.ex:787-792 `rounds_played_count/1` is O(N·R); standings.ex:591-593 and 596 call the adjusted-score path 3-5 times over per entry; standings.ex:561 shows `by_id` is immutable for the whole run.

Concrete: 300 players, 11 rounds, PlayersLive grid (BH+BHC1+SB → 3 passes). adjusted_score calls = 3 × 300 × 11 = 9,900. Each does 300 Map.values traversals with a `length/1` over an 11-element list ≈ 3,300 element steps, plus an 11-element sort. Total ≈ 33M element steps per render — hundreds of milliseconds to low seconds on BEAM, re-paid on every result entry. At 100 players / 9 rounds it is ≈ 2.4M steps, still tens of ms per broadcast.

**Fix.** Two changes, both local to `compute_tiebreaks/3`: (1) compute `rounds_played_count(by_id)` once there and thread the integer into `adjusted_score/3`, `tiebreak("KS", ...)` and `buchholz_contributions/3` — this alone removes the N factor and takes adjusted_score to O(R log R); (2) precompute `%{player_id => adjusted_score}` for all N entries once (N × O(R log R)) and have `buchholz_contributions/3` and `tiebreak("SB", ...)` do a map lookup. That collapses the whole tiebreak block from O(N²R²) to O(N·R·C). Memoizing `buchholz_contributions/3` per entry across the BH/BHC1/BHC2/MBH codes is a further constant-factor win.
