# Codebase sweep, 2026-08-26

A deliberate read of the whole of OpenPairings looking for bugs,
optimizations and things worth adding - not a response to a bug report.
Twenty broad-scope readers across the two repositories, with every
bug-severity claim then handed to a separate reader told to *refute* it.

Nothing here has been fixed. This is the list; acting on it is a separate
decision per item. The Ainalrami half is in that repo's
`docs/sweep-2026-08-26.md`.

## What the sweep was aimed at

One shape above all: **the same rule written down twice, where the copies
drift apart silently.** That is the shape behind every real bug found in
0.17.1 - a played-code list that lost `W`/`D`/`L`, a bye scored from its
TRF letter instead of its kind, an options list written out twice - and it
is the shape that unit tests are worst at catching, because both copies
are individually consistent.

It found more of them. The three highest-value bugs below are all that
shape, and two are direct siblings of the ones fixed yesterday: the same
`W`/`D`/`L` vocabulary, missed in two *other* private copies.

## The headline

**Three confirmed, independently re-verified bugs**, each traced end to
end:

1. **A TRF that OpenPairings exported cannot be re-imported without data
   loss.** `TrfImport` keeps a private `@playing_codes` that never gained
   `W`/`D`/`L`, so every unrated played game fails to resolve to a mutual
   pairing and is reinterpreted as a **bye** - the opponent is lost. The
   proof it was meant to work: `result_string("W", _) -> "1-0U"` sits three
   lines below, unreachable.
2. **Keizer standings crash** (`CaseClauseError`) the moment an asymmetric
   `1/2-0` result is entered. `classify_result/2` emits `:half_win` and
   `:half_loss`; `round_stats/2` - the other consumer of that vocabulary,
   in the same module - lists nine classes, neither of those, and has no
   catch-all.
3. **JSON backup and snapshot restore destroy every round's pairing
   rationale.** `@round_fields` omits `Round.explanation`, with no comment
   giving a reason and no test pinning the list.

The first two I re-read and confirmed by hand after the agents reported
them; the third's evidence is checkable in one grep.

## Bugs (14)

### Keizer standings crash (CaseClauseError) as soon as an asymmetric "½-0"/"0-½" result is entered

`lib/pairings_engine/keizer.ex:232`

`classify_result/2` emits `:half_win`/`:half_loss` for the VCL.13 asymmetric results (keizer.ex:539-542), and `class_points/4` was extended to handle them (keizer.ex:566-567). `round_stats/2` — the OTHER consumer of the same class vocabulary, in the same module — was not: its `case e.class do` at keizer.ex:234 lists only `:win, :draw, :loss, :zero, :forfeit_win, :forfeit_loss, :unpaired_bye, :excused, :not_joined` and has no catch-all clause (the `end` is at keizer.ex:281). A `:half_win` or `:half_loss` entry therefore raises `CaseClauseError`.

This is the classic shape: one result vocabulary, two consumers, only one updated when the vocabulary grew. `score_all/5`'s own @doc (keizer.ex:462-464) even names `:half_win`/`:half_loss` as members of the set, so the doc and `class_points/4` agree and only `round_stats/2` is out of step.

Blast radius is everything that calls `Keizer.standings/2`: `PairingsEngineWeb.LiveRoundLive` (live_round_live.ex:116), `PrintController` (print_controller.ex:822-823), `PairingRationale` (pairing_rationale.ex:627, 649), and `Standings.player_scores_before_round/2` (standings.ex:127) — i.e. the next round's pairing sheet also dies, not just the standings table.

**Evidence.** keizer.ex:539-542

      {"1/2-0", false} -> :half_loss
      {"0-1/2", true} -> :half_loss
      {"0-1/2", false} -> :half_win

keizer.ex:232-234, 279-281
  defp round_stats(entries, t) do
    Enum.reduce(entries, %{played: 0, wins: 0, draws: 0, losses: 0, raw_points: 0.0}, fn e, acc ->

        ...

Concrete input: a Keizer tournament; on the results page (`pairings_live.ex:25` offers `{"1/2-0", "½-0 (asymmetric - disciplinary point adjustment)"}` with no per-pairing-system gating, and `Tournaments.Pairing` accepts it at tournaments/pairing.ex:28) record board 1 of round 1 as "1/2-0". `Keizer.standings(tournament)` -> `round_stats/2` -> `e.class == :half_win` -> CaseClauseError. The standings page, the printed standings, the round-N+1 pairing sheet and the pairing rationale all 500.

**Fix.** Add `:half_win` and `:half_loss` clauses to `round_stats/2`, scored the way `score_all/5`'s doc already says they are — `:half_win` like `:draw` (played+1, draws+1, `raw_points + t.points_draw`), `:half_loss` like `:loss` (played+1, losses+1, `raw_points + t.points_loss`). Consider deriving both consumers from one `class -> {played?, wdl, raw_points}` table so the next class added cannot split them again.


### bye_safe_result's played-code list also missed W/D/L - an opponentless unrated result crashes TRF export and the pairing run

`lib/pairings_engine/pairing.ex:2178`

`bye_safe_result/2` is documented as the single choke point that guarantees "opponent 0000 may only ever carry a bye/unplayed code", and its case lists `["1", "+"] -> "F"`, `"=" -> "H"`, `["0", "-"] -> "Z"` - the pre-W/D/L played-code set. When `Pairing.@results` and `Trf.@playing_codes` gained "W"/"D"/"L", this list was not updated, so those three fall into the `other -> other` passthrough and emit a dangling playing code against 0000.

`Trf.validate_games!/2` then raises (trf.ex:514-519, `opponentless games must use a bye code (F/H/Z/U)`) because `serialize/1` never passes `allow_dangling_playing_code`. `TrfExport.export/2` rescues that into `{:error, _}`, but `Pairing.javafo_input/4` calls `Trf.serialize/1` unguarded (pairing.ex:1464) - the two `rescue` clauses in that module (lines 1016/1030) only wrap the Ainalrami invocation - so pairing the next round raises instead of pairing.

**Evidence.** pairing.ex:2178-2185

    case result do
      code when code in ["1", "+"] -> "F"
      "=" -> "H"
      code when code in ["0", "-"] -> "Z"
      other -> other
    end
  end

Reachable state: priv/repo/migrations/20260709170320_create_core_tables.exs:86-87 declares both seats `references(:players, on_delete: :nilify_all)`, and `Tournaments.delete_player/1` (tournaments.ex:1346) is a plain `Repo.delete/1` that does not clear results. Delete a player who lost an unrated game: the surviving opponent's pairing keeps `result: "1-0U"` with `black_player_id` now nil. `trf_game/3` maps `{"1-0U", true} -> "W"` (pairing.ex:2129), `bye_safe_result("W", nil)` returns "W" unchanged, and the next TRF export errors while the next "Pair round N" raises Trf.ValidationError. **Fix.** Extend the mapping to the full played set: `["1", "+", "W"] -> "F"`, `["=", "D"] -> "H"`, `["0", "-", "L"] -> "Z"`.


### ensure_pairing_numbers/2 takes max_existing over the ACTIVE subset, so a new player can be handed a pairing_number already held by an absent/withdrawn one

`lib/pairings_engine/pairing.ex:263`

The docstring (pairing.ex:251) says numbers continue "from the current max existing number", but the code takes the max over the `players` list it was handed, and BOTH callers hand it the active-only subset: `Pairing.pair_next_round/1` (pairing.ex:104,120) and `Keizer.do_pair/4` (keizer.ex:126) both pass `active_players/1`, which excludes `status != "active"`, `absent == true` and `forfeit == true`. Any of those three flags on the highest-numbered player removes their number from the max computation while the number itself stays frozen on the row. There is no unique index and no changeset validation on `pairing_number` (priv/repo/migrations/20260709183000_add_pairing_number.exs:8 adds a plain `:integer`; Player.changeset at lib/pairings_engine/tournaments/player.ex:80-113 has no uniqueness check), so the duplicate is written without complaint. `guard_pairing_number_freeze/2` (tournaments.ex:1322) only guards CHANGING an existing number and explicitly permits nil -> N.

The module already has the right set for this question: `full_roster_players/1` (pairing.ex:1895) and `build_shared_history/1` (pairing.ex:2073) both define "every player who ever received a pairing_number" precisely because a rank question must not be scoped to the currently-eligible pool. `max_existing` is the one place that rule is written a second time, over the wrong set.

Blast radius: the live pairing run survives (do_pair_single remaps to a local contiguous 1..M map), but PairingsEngine.TrfExport emits `trf_player_rows/3` rows with the RAW `pairing_number` as `:rank` (pairing.ex:1752), so the downloadable FIDE TRF carries two rows with the same starting rank. Worse, `Trf.validate_games!/2` builds `by_rank = Map.new(players, &{&1[:rank], &1})` (trf.ex:493), which silently collapses the two, so `validate_playing_pair!/5` cross-checks games against the wrong player and can raise a bogus `Trf.ValidationError` that kills the download outright. `order_for_pairing/3` also uses `pairing_number` as its final tie-break (pairing.ex:1885) — the tie-break whose own comment says it exists so the order is reproducible — and two players sharing it puts that back to `Enum.sort_by` stability.

### player_points/2 omits SWAR 3-2-1 presence points that Standings adds, so the TRF score column (and the engine's bracket) disagrees with the crosstable

`lib/pairings_engine/pairing.ex:1831`

`player_points/2` is the number written into TRF columns 81-84 and the number `order_for_pairing/3` sorts the engine's input rows by. Its own docstring (pairing.ex:1778-1781) states the requirement: "It therefore has to equal what `PairingsEngine.Standings` puts in the crosstable, and for a long time it did not." It lists the two drifts it fixed (W/D letter codes, and bye letters vs bye kinds). There is a third it does not handle.

`Standings.pairing_records/4` adds SWAR's 3-2-1 presence point on top of every played game's result value (standings.ex:465 and :491, `points: wp + presence_points(t, w_present?)`). `game_points/3` has no presence term at all. `presence_value` is set only by `SwarImport.scoring_attrs/1`'s `%{type: 3}` clause (swar_import.ex:1256-1264), i.e. Belgian 3-2-1 club events — a supported, real-data-tested import path (docs/swar-import.md:478 names the real fixture) whose whole point is continuing the event in OpenPairings.

Standings' own comment (standings.ex:503-505) records that SWAR itself sends `Points + SpecialPts` in the TRF it hands JaVaFo (EnvoiJAVAFO.cpp:250) — so this app is knowingly sending a different column than the program it was reverse-engineered from. And the shift is not uniform: standings.ex:511 spells out that presence is per round ATTENDED, so relative order between an attender and a non-attender genuinely changes.

### A pairing-allocated bye stored as a Pairing row scores plain bye_value in the TRF, skipping the presence_on_allocated_bye bonus that Standings and engine_point_system both apply

`lib/pairings_engine/pairing.ex:1834`

There are two storage shapes for a bye and only one of them reaches the shared rule. A `byes`-table row of type "pairing-allocated" carries `points_kind: "pairing-allocated"`, which is in `@bye_kinds` (pairing.ex:1822) and therefore routes to `Standings.bye_points/4` — the function `player_points/2`'s docstring calls "the same function the crosstable calls, rather than a second opinion about the same rule". The TRF score column is the one remaining copy that still says `bye_value` alone.

### bye_safe_result/2 never learned the unrated W/D/L codes, so an opponentless unrated game raises Trf.ValidationError and takes down the pairing run

`lib/pairings_engine/pairing.ex:2178`

`bye_safe_result/2` exists to guarantee TRF16's rule that opponent 0000 may only carry a bye code, and its comment enumerates the reinterpretation: "a win or forfeit-win is a full-point bye (F), a draw is a half-point bye (H), a loss or forfeit-loss is a zero-point bye (Z)". The mapping lists 1, +, =, 0, - — the rated codes. TRF16's played-but-unrated twins W/D/L were added later and are canonically enumerated in `Trf.@playing_codes` (trf.ex:101, `~w(1 = 0 + - W D L)`), and `game_points/3` right next door knows about them (`~w(1 + F W)`, `~w(= H D)`, pairing.ex:1833-1835). `bye_safe_result/2` was not updated, so W/D/L fall through its `other -> other` catch-all and stay playing codes with a nil opponent.

`Trf.validate_games!/2` — which `Trf.serialize/1` always runs without `allow_dangling_playing_code` — then raises for exactly that combination (trf.ex:513-519). The raise happens while BUILDING the TRF, i.e. before `run_engine/5` is ever called (pairing.ex:391-394), so `run_ainalrami/4`'s `rescue e in Ainalrami.Trf.ValidationError` clause (pairing.ex:1052) cannot catch it either. It escapes `pair_next_round/1` entirely and crashes the caller instead of returning the `{:error, string}` every other refusal in this module returns. `PairingsEngine.TrfExport` goes through the same `trf_player_rows/3` -> `Trf.serialize/1` path, so the FIDE download 500s too.

The rated twin of the identical situation works fine — `"1-0"` becomes `"1"` becomes `"F"` — which is what makes this a silent drift rather than an obvious hole.

### Round-robin rounds_count auto-correction crashes when the derived total exceeds the changeset's 30-round cap

`lib/pairings_engine/round_robin.ex:322`

`ensure_correct_rounds_count/2` computes the schedule's real length and forces it onto the tournament with a hard `{:ok, updated} =` match. `Tournament.changeset/2` caps `rounds_count` at 30 (`validate_number(:rounds_count, greater_than: 0, less_than_or_equal_to: 30)`, tournament.ex:498), so any schedule longer than 30 rounds makes `update_tournament/2` return `{:error, %Ecto.Changeset{}}` and the match raises `MatchError` - an unhandled crash out of `pair_next_round/1`, not the `{:error, reason}` the LiveView is written to display.

The two sides were written independently: the cap is a UI-scale sanity bound on a Swiss field, and `total_rounds/2` (181) / `match_total_rounds/1` (238) derive a number that has nothing to do with it.

**Evidence.** round_robin.ex:311-325:
```
defp ensure_correct_rounds_count(tournament, frozen_count) when frozen_count >= 2 do
  correct = if tournament.rr_match_format, do: match_total_rounds(frozen_count), else: total_rounds(frozen_count, tournament.rr_cycles)
  if tournament.rounds_count == correct do
    tournament
  else
    {:ok, updated} = Tournaments.update_tournament(tournament, %{rounds_count: correct})
```
Concrete input: a tournament with `pairing_system: "round_robin"` and 32 active players (`total_rounds(32, 1) == 31`), or 17 players with `rr_cycles: 2` / `rr_match_format: true` (`== 34`). Click "Pair round 1": `ensure_correct_rounds_count/2` runs before any other guard (line 100, before `paired`/`length(frozen)` are even checked), the changeset rejects 31/34, and the match raises.

**Fix.** Handle the error tuple: `case Tournaments.update_tournament(...) do {:ok, updated} -> updated; {:error, changeset} -> ...` and surface it as a real `{:error, reason}` from `pair_next_round/1` ("a round robin with N players needs M rounds, above the 30-round maximum"), or raise the changeset's cap to the largest schedule a round robin can actually produce.


### @round_fields omits Round.explanation - JSON backup and snapshot restore silently destroy every round's pairing rationale

`lib/pairings_engine/tournament_export.ex:106`

`Round` has five content fields: `number`, `date`, `status`, `published_at` and `explanation` (rounds.ex - `field :explanation, :map`). `@round_fields ~w(number date status published_at)a` lists only four, and unlike `@tournament_fields`/`@excluded_tournament_fields` there is no comment giving a reason and no guard test (test/pairings_engine/tournament_export_test.exs only pins the *tournament* field list; nothing pins rounds, players or pairings). So `explanation` is dropped with no trace.

This is not backup-only. `PairingsEngine.Snapshots` uses this exact envelope (snapshots.ex:82 `TournamentExport.export_tournament/1`, snapshots.ex:374 `TournamentImport.restore_into!/2`), so restoring any restore point wipes the stored engine explanation for every round in the tournament. The Round schema comment states precisely why that matters: the explanation is "a record of what happened, not a derivation of current state", stored because re-deriving after a hand edit "would explain a pairing the engine never produced". After a restore the rationale page falls back to exactly that reconstruction.

**Evidence.** tournament_export.ex:106  @round_fields ~w(number date status published_at)a
tournament_export.ex:143  defp round_map(round) do
                             round |> struct_fields(@round_fields) |> Map.merge(...)

rounds.ex (schema)  field :explanation, :map

**Fix.** Add `explanation` to @round_fields (it is already cast by Round.changeset/2), and extend tournament_export_test.exs's schema-drift guard to cover Round, Player and Pairing the same way it already covers Tournament.


### JSON/snapshot restore silently clears special_table for SWAR-imported fixed-table players

`lib/pairings_engine/tournament_import.ex:173`

`@player_fields` correctly exports both `special_table` and `fixed_board`, so the envelope always contains a `"fixed_board"` key - even when its value is nil. `import_players!` feeds that whole map straight into `Player.changeset/2`, whose `sync_special_table/1` fires on key *presence*: `if Map.has_key?(changeset.params || %{}, "fixed_board")` then `put_change(:special_table, not is_nil(get_field(changeset, :fixed_board)))`. The exported `special_table: true` is therefore overwritten with false.

The comment on `sync_special_table/1` names exactly the state this breaks: "Other writers - notably the SWAR importer, which sets `special_table` directly from HandyTable without going through `fixed_board` at all - never include `fixed_board` in their attrs, so this leaves their value alone." ### `adjusted_score/3` compares a record COUNT to a round NUMBER — one entered result inflates every un-reported player's Buchholz/SB by a draw

The persistent case is a board whose result is never filled in at all — those two players then permanently hand a phantom draw to everyone who played them.

### Per-category Swiss pairing rebuilds the identical full-roster TRF (and re-runs 3 DB queries) once per category

`lib/pairings_engine/pairing.ex:690`

`do_pair_by_category/3` correctly hoists `build_shared_history/1` out of the category loop (pairing.ex:441) — but everything downstream of it is still recomputed per category. `compute_category_group/8` calls `build_category_trf/5` once per group (pairing.ex:547), and inside it:

```elixir

  tournament
  |> trf_player_rows(full_roster, shared_history)      # identical every call
  |> mark_ineligible_for_round(eligible_ids)           # <-- the ONLY per-category part
  |> remap_trf_rows_to_local_ranks(local_rank_by_player_id)  # identical every call
  |> Enum.sort_by(& &1.rank)                           # identical every call

# ... Trf.serialize(...) over the full roster        -- identical every call

         paired_rounds_count(tournament.id) + 1,      # pairing.ex:725 - DB aggregate, per category
         local_rank_by_player_id) <>
  forbidden_pairs_lines(tournament.id, full_roster, local_rank_by_player_id) <>   # pairing.ex:730
  exclusion_pairs_lines(tournament, full_roster, local_rank_by_player_id)         # pairing.ex:731
```

`full_roster`, `local_rank_by_player_id`, `shared_history` and `tournament` are all computed once in `do_pair_by_category/3` (pairing.ex:441-516) and passed through unchanged, so every one of those steps is a pure function of loop-invariant inputs.

Two costs stack:

1. **CPU.** `trf_player_rows/3` → `games_per_player/3`, whose body (pairing.ex:2002-2007) is `for {player_id, _} <- by_id` × `Enum.map(rounds, ...)` × `Enum.find(round.pairings, ...)` — an O(N²R/2) list scan, repeated once per category. `Trf.serialize/1` over the full roster is repeated too.

2. **Queries.** `paired_rounds_count/1` is a `Repo.aggregate` (pairing.ex:231). `forbidden_pairs_lines/3` and `exclusion_pairs_lines/3` *each* call `Tournaments.list_forbidden_pairings/1`, which is `Repo.all` **plus `preload: [:player_a, :player_b]`** (tournaments.ex:1741-1748) — 3 queries per call. Neither caller ever touches the preloaded structs; both read only `fp.player_a_id` / `fp.player_b_id` (pairing.ex:1522, 1544). So each `build_category_trf/5` costs 1 aggregate + 6 preload-inflated queries = 7, all returning identical rows.

(The same double `list_forbidden_pairings/1` call — 6 queries where 1 lean one would do — is in the single-bracket path too, at pairing.ex:1497-1498.)

**Evidence.** pairing.ex:547 `build_category_trf(...)` inside `compute_category_group/8`, which `compute_category_pairs/6` runs per group (pairing.ex:491-506); pairing.ex:695-731 the recomputed body; pairing.ex:441 and 505-516 showing `shared_history`, `full_roster` and `local_rank_by_player_id` are loop-invariant; pairing.ex:1999-2010 `games_per_player/3`'s O(N²R) `Enum.find` over `round.pairings`; tournaments.ex:1741-1748 `list_forbidden_pairings/1` with the unused `preload: [:player_a, :player_b]`; pairing.ex:1520 and 1543 the two calls.

Concrete: 300 players, 9 rounds, 5 categories. `games_per_player/3` does 300 × 9 × ~150 ≈ 405k comparisons per call; run 5 times ≈ 2M, where 405k would do. Query count for the round goes from ~4 to ~35. Pairing is the slowest user-facing action in the app, so this is directly felt.

**Fix.** Hoist the loop-invariant work into `do_pair_by_category/3` and pass the results down: compute `trf_player_rows |> remap_trf_rows_to_local_ranks |> Enum.sort_by(& &1.rank)` once (`mark_ineligible_for_round/2` only appends a game with `opponent_rank: nil`, which `remap_trf_rows_to_local_ranks/2` leaves alone and which does not change `:rank`, so moving it after the remap is behaviour-preserving), and compute the `acceleration_lines`/`forbidden_pairs_lines`/`exclusion_pairs_lines` suffix once. Separately, give `forbidden_pairs_lines/3`/`exclusion_pairs_lines/3` an id-only query instead of `list_forbidden_pairings/1` (they never read the preloads), and pass the fetched list between the two rather than querying twice. Expected: category-pairing CPU and query count both drop by the category count; the preload removal is a further 3x on those queries everywhere.

### Standings tiebreaks are O(N²R²): a whole-field scan runs inside the per-game inner loop, and adjusted_score is never memoized

`lib/pairings_engine/standings.ex:695`

`adjusted_score/3` is the inner loop of every Buchholz-family and SB tiebreak, and it opens by recomputing a value that is constant for the entire standings run:

```elixir
# standings.ex:693
defp adjusted_score(opp_entry, by_id, t) do
  games = Enum.sort_by(opp_entry.games, & &1.round)
  total_known_rounds = rounds_played_count(by_id)   # <-- line 695
```

```elixir
# standings.ex:787
defp rounds_played_count(by_id) do
  by_id |> Map.values() |> Enum.map(&length(&1.games)) |> Enum.max(fn -> 0 end)
end
```

`by_id` is built once in `compute_tiebreaks/3` (line 561) and never mutated, so `rounds_played_count(by_id)` returns the same number every time — but it walks all N entries and calls `length/1` on each R-element game list on every call, i.e. O(N·R) per call.

Call count: `buchholz_contributions/3` (line 678) calls `adjusted_score` once per game, and is itself called separately for BH, BHC1, BHC2 and MBH (lines 591-593) with no memoization; `tiebreak("SB", ...)` (line 596) calls `adjusted_score` per game again. `adjusted_score` is also recomputed from scratch for the same opponent every time a different player faced them, even though only N distinct answers exist. `tiebreak("KS", ...)` at line 635 calls `rounds_played_count(by_id)` once per entry as well.

Net: O(N²R²) per standings computation. Nothing is cached — I checked for ETS/persistent_term/Cachex and the only ETS tables in the app are rate limiters and the tools session store.

This is not a cold path. `PlayersLive.assign_players/1` calls `Standings.grid_standings/1` (players_live.ex:167), which forces `~w(BH BHC1 SB PS DE)` on top of the tournament's configured codes (standings.ex:54) — so at least three adjusted-score passes run regardless of configuration. `assign_players/1` runs on mount AND on every `{:tournament_changed, ...}` broadcast (players_live.ex:139-159), in every connected PlayersLive process, i.e. every time any arbiter enters any result.

**Evidence.** standings.ex:695 `total_known_rounds = rounds_played_count(by_id)` inside `adjusted_score/3`; standings.ex:787-792 `rounds_played_count/1` is O(N·R); standings.ex:591-593 and 596 call the adjusted-score path 3-5 times over per entry; standings.ex:561 shows `by_id` is immutable for the whole run.

Concrete: 300 players, 11 rounds, PlayersLive grid (BH+BHC1+SB → 3 passes). adjusted_score calls = 3 × 300 × 11 = 9,900. Each does 300 Map.values traversals with a `length/1` over an 11-element list ≈ 3,300 element steps, plus an 11-element sort. Total ≈ 33M element steps per render — hundreds of milliseconds to low seconds on BEAM, re-paid on every result entry. At 100 players / 9 rounds it is ≈ 2.4M steps, still tens of ms per broadcast.

**Fix.** Two changes, both local to `compute_tiebreaks/3`: (1) compute `rounds_played_count(by_id)` once there and thread the integer into `adjusted_score/3`, `tiebreak("KS", ...)` and `buchholz_contributions/3` — this alone removes the N factor and takes adjusted_score to O(R log R); (2) precompute `%{player_id => adjusted_score}` for all N entries once (N × O(R log R)) and have `buchholz_contributions/3` and `tiebreak("SB", ...)` do a map lookup. That collapses the whole tiebreak block from O(N²R²) to O(N·R·C). Memoizing `buchholz_contributions/3` per entry across the BH/BHC1/BHC2/MBH codes is a further constant-factor win.

**Evidence.** lib/pairings_engine/standings.ex:466
