# Codebase sweep, 2026-09-01

A deliberate read of the whole of OpenPairings looking for security
problems, bugs and things that are not optimal - not a response to a bug
report. Six broad-scope readers over disjoint slices of this repository
(security surface, pairing and standings core, parsers and exports, the two
halves of the web layer, and infrastructure), each told to default to "not
a finding" when uncertain. **Every claim was then checked against the
source by the orchestrator before it went in here**, and the six whose
mechanism is dynamic - a crash between two autocommits, a race, a crafted
header - were handed to a seventh reader whose only job was to reproduce
or refute them with a throwaway test.

The Ainalrami half is in that repository's `docs/sweep-2026-09-01.md`.

The dependency and runtime layer was checked separately from the code, by
hand, against published advisories. It is clean; see **Runtime layer**.

### The prior audit, adjudicated

An `AUDIT_REPORT.md` (untracked, 923 lines) sat in the working tree at the
start of this sweep, with six findings and a tunnel threat model. Each
claim was checked against the source rather than inherited:

* **Confirmed**: no timeout on the JaVaFo `System.cmd` (`pairing.ex:1005`);
  `RateLimit.record/2` is lookup-then-insert (`rate_limit.ex`); the
  enrollment `code` index is not unique and `gen_unique_code/1` is
  read-then-insert (`mobile.ex`, and see M7 for the consequence); an empty
  slug for a non-Latin tournament name (`export_controller.ex:132-137`);
  `TRUSTED_PROXY_HOPS` unset in prod, so every visitor shares one rate-limit
  bucket - the deploy script's unit never sets it.
* **Its proposed rate-limiter fix is still not atomic** - it does the same
  lookup-then-insert with `update_counter` on one branch only. The real fix
  is `:ets.update_counter/4` with a default, or a single-writer process.
* **Refuted as written**: the "critical" local-mode auto-login trap behind
  the tunnel. The mechanism is real (`user_auth.ex:106-121` signs in any
  loopback client when `local_mode?`), but prod is not local mode, and
  local mode pins the listener to `127.0.0.1` in `runtime.exs:377` - the
  two are set by the same flag. It is a documentation warning, not an
  exposure.

  fixes (CVE-2026-11822/11824); sqlite.org lists nothing fixed later.

  req 0.7.4, swoosh 1.28, burrito 1.6, telemetry_metrics 1.2.

## What the sweep was aimed at

Authorization and tenancy, token handling, hostile input through every
parser, atomicity of multi-row writes, races between two arbiters, the
public no-account surfaces (`/tools`, `/m`, `/locale`), the deploy path,
supply chain, and the tests' ability to fail. The readers were told what
the August sweep had already closed and pointed at the 84 commits since,
where new defects concentrate. They were also handed the prior audit's six
claims as things to beat rather than repeat.

## The three worth reading first

**H2.** The `swap_seated_with_pool_player/3` gap is the third of three
seating writes the August sweep's own fix paragraph named
(`docs/sweep-2026-08-26.md:792`); the shipped commit patched two. Two
readers found it independently from opposite ends - one from the context
layer (no `player_belongs_to_tournament?` check, unlike `fill_seat/3` at
`:2517` and `pair_from_pool/4` at `:2677`), one from the LiveView (the
confirm dialog validates `pool_member?` once at staging and
`refresh(keep_gesture: true)` deliberately keeps it open across another
arbiter's edit). Together they make it reachable through ordinary use: open
"swap with…" for pool player Y on board 3, pair Y onto board 7 in another
tab, confirm the first dialog. Y is on two boards, `{:ok, _}` is returned.

**H3.** `extra_arbiters_count` reaches the server through `update_fields`
on the public tools page (`tools_norms_live.ex:130-134` merges any overlay
key unvalidated), is parsed without a ceiling in three places, and drives
two `Enum.map_join(1..n, …)` calls in `ItThreeExpand.expand/2`. Measured on
the real IT3 template: ~106 bytes and ~0.07 ms per extra arbiter, linear
(1,002 extras → 122 KB in 70 ms). One request with `100000000` is ~10 GB of
string building. No account, no upload, one field.

**H1.** `read_existing_secret_key_base/2` in the deploy script `cat`s the
previous systemd unit through `run_ssh_command/2`, which prints every
line of output. The unit carries `SECRET_KEY_BASE`, the SMTP password, the
notice token and the KBSB key. The function's own docstring says "Never
print the value"; the quiet variant `run_ssh_quiet/2` exists twenty lines
below and is used for the health poll. The notice token is separately
echoed on every deploy because `announce_deploy_notice` puts the bearer
in the command string that `run_ssh_command` prints first. The
maintainer's own to-do to "rotate secrets from scrollback" is this bug.

## Findings

Severity-ordered. Each carries the reader's evidence, the orchestrator's
verification, and where relevant the refuter's verdict.

### H1 · Every redeploy prints the box's secrets to stdout

`deploy_openpairings.py:204-215` (`run_ssh_command/2`: `if out.strip():
print(out)`), `:332-334` (`read_existing_secret_key_base/2` calls it with
`cat /etc/systemd/system/{unit}`), `:248-253` (`announce_deploy_notice`
interpolates the bearer into the command string, which `:205` prints).

Trigger: any deploy of an app that already has a unit - every deploy but
the first. Effect: the full secret set in terminal scrollback, `tee`'d
logs, screen shares. `SECRET_KEY_BASE` is a session-forgery primitive.

Fix: call `run_ssh_quiet` at `:332` and in both notice functions, and have
`run_ssh_command` redact a short list of known env names as a second
layer. Then rotate what has already been printed.

Verified by reading the three functions. The script is outside the
repository (`C:\Users\jorian\Desktop\deploy_openpairings.py`).

### H2 · A stale substitution dialog seats one player on two boards

`tournaments.ex:2739-2768`; reached from `pairings_live.ex:829-838`.

`swap_seated_with_pool_player/3` re-locates `seated_id` in the fresh round
(`find_player_seat/2`) but never checks `pool_id` - not for tournament
membership, not for "still unseated". `Pairing.changeset/2` casts the seat
columns with no validation and `pairings` has no unique constraint on
`(round_id, player)`. `apply_confirm/2` passes `pool_id` straight from
`socket.assigns.confirm`, staged possibly minutes earlier; `handle_info`
keeps the gesture alive across a remote change by design (`:127-135`).
Contrast `do_pair_from_pool/4` (`:2685-2691`), which re-checks the board
inside its transaction, and `swap_players_in_round/3`, which re-locates
both sides.

Trigger: two tabs or two arbiters, as above. Effect: one player in two
pairings of one round, the displaced player benched with a fresh `byes`
row, no error.

Fix: inside the transaction, `player_belongs_to_tournament?/2` and a
"not already seated in this round" check on `pool_id`, returning the
`:invalid_player` tag the siblings already use; a test mirroring
`tournaments_test.exs:1489` for this third function.

### H3 · One form field on the public tools page builds gigabytes of XML

`tools/overlay.ex:76-90` (`Enum.reduce(1..count, …)`), `norms/forms.ex:197-205`
(unbounded parse), `norms/it_three_expand.ex:93-100` and the two
`Enum.map_join(1..insert_count, …)` sites, `tools_norms_live.ex:130-134`
(`update_fields` merges the raw overlay) and `:560-571` (`add_arbiter`
floors at 0, no ceiling).

Measured: see above. Three readers filed this independently. The refuter
drove the `add_arbiter` click path to 20,000 and found it cheap - ~1.2 ms
per click, 0.2 ms per render, 88 KB of process growth - so the cost is not
in the LiveView's own rendering. It is in what the count *drives*: a
single `update_fields` with `overlay[extra_arbiters_count]=100000000` skips
the clicks entirely, and the next report download runs
`ItThreeExpand.expand/2` over that count.

Fix: clamp at the parse - `parse_extra_count/1` in `overlay.ex`,
`extra_arbiters_count/1` in `forms.ex`, `bump_extra_arbiters/2` and
`update_fields` in the LiveView - to a small constant. FIDE norm reports
need a handful.

### M1 · The service runs as root

`deploy_openpairings.py:1109-1116`: `User=root`, no `NoNewPrivileges`,
`ProtectSystem`, `ProtectHome`, `PrivateTmp`, `ReadWritePaths`. No
`useradd` anywhere in the script. The app shells out to `java` and
`bbpPairings` with tournament data, and any bug in ~30 transitive
dependencies is root on a box that also hosts OpenResults.

Fix: a system user owning the app tree, database and backup directories;
`User=`/`Group=` plus the four hardening directives. `PORT` is above 1024.

### M2 · The deploy accepts any SSH host key, every run

`deploy_openpairings.py:1639-1644`: `AutoAddPolicy` and nothing ever
loads or persists known hosts (no `load_system_host_keys`, no
`known_hosts`, confirmed by grep). The default user is root and the auth
path is a typed password. A network-position attacker takes the root
password.

Fix: `load_system_host_keys()` + `RejectPolicy`, and key-based auth - the
project's own rule already forbids password SSH.

### M3 · Round un-pairing is two autocommits

`pairing.ex:227-234`: `Repo.delete_all` on `rounds`, then on `byes`, no
`Repo.transaction`. Every round-*creation* path in the module wraps Round
+ Pairings + byes in one transaction, and `keizer.ex:474-478` explains why.
A crash between the two leaves orphan `byes` rows. Every bye insert uses
`on_conflict: :nothing` (`pairing.ex:940, 1516`; `keizer.ex:205`;
`round_robin.ex:473`), so on re-pairing the orphan wins; and
`Standings.add_bye_records/3` (`standings.ex:643-690`) appends a bye record
with no check that the player already has a real game that round.

Refuter: **reproduced.** A Round-only delete left the absent-bye row; re-pairing the round with that player seated on a real board, `Standings.standings/1` gave her **2.0 points for a 1.0 win** - the orphan bye stacked on the game.

Fix: one transaction around both deletes; optionally a membership guard in
`add_bye_records/3`.

### M4 · A rejected restore still moves HEAD

`snapshots.ex:349-358`: `capture(… "snapshot.restored" …, pinned: true)`
and `set_head/2` are plain committed writes; only `do_restore/2`
(`:380-397`) runs in a transaction. `TournamentImport.restore_into!/2`
rolls back cleanly on a changeset error, `HistoryLive` shows "Could not
restore: …", and the tournament's data is untouched - but
`head_snapshot_id` now points at the target and a "Before restoring to …"
snapshot exists. The next `capture/4` hangs its `parent_id` off the wrong
node (`:92`).

Trigger: restoring an older snapshot whose payload no longer validates
against the current changesets; plausible on a long-running tournament
with snapshots 50 deep and several ships a day.

Fix: move both HEAD writes inside the restore transaction, or defer them
until it succeeds.

### M5 · Password-login rate limit keyed on the raw socket address

`user_session_controller.ex:99-106` builds `{:login_client,
:inet.ntoa(conn.remote_ip)}`. `RateLimit`'s moduledoc says callers must
use `ClientIp`; `user_live/login.ex:248` and `mobile_enroll_controller.ex:21`
do. Today this collapses anyway (hops = 0), but it stays wrong after
`TRUSTED_PROXY_HOPS=1` is set: thirty wrong passwords from anywhere lock
password login for the whole site for fifteen minutes.

Fix: `ClientIp.get(conn)`.

### M6 · Two concurrent Accepts create two players

`registrations.ex:233-269`: `accept/1` reloads and checks `"pending"`,
then `do_accept/1` creates the player and does an unconditional
`Repo.update!` with no status guard and no transaction. SQLite serialises
the writes, not the read-then-write window.

Refuter: **reproduced** with two concurrent `Task.async` calls to `accept/1` - **two players from one registration**, identical across four seeds. Sequential calls on a stale struct are safe; `accept/1` genuinely reloads.

Fix: the transition as the guard - `update_all` with `where: status ==
"pending"` returning the row count, the pattern `Publishing.ensure_key/1`
uses.

### M7 · Duplicate enrollment codes turn the public submit into a 500

`mobile.ex:60-68`: `Repo.one` raises `Ecto.MultipleResultsError` on two
matches; `:118-138`: uniqueness is a read-then-insert across all
tournaments and gives up after 20 attempts returning a possibly-duplicate
code; the migration indexes `code` non-uniquely. The public code-submit
route has no rescue.

Refuter: **reproduced.** Two active enrollments with one code raise `Ecto.MultipleResultsError` from `get_active_by_code/1` and through `POST /m`; nothing on that path rescues.

Fix: a partial unique index on active codes, or `Repo.all |> List.first`
plus a retry on conflict; and the known atomic-generation fix.

### M8 · One invalid SWAR player crashes the whole import

`swar_import.ex:1572-1577`: `{:ok, player} = Tournaments.create_player(…)`
with no other clause. `create_player/2` returns `{:error, changeset}` for a
blank name, a FIDE id out of range, a name over 100 characters.
`build_player_structs/2` (`:662-677`, the pure path the tools page uses)
handles it correctly thirty lines away, and so does `TrfImport`. The
commit runs inside `Repo.transaction` (`:698`), so the database rolls back
- but the LiveView dies instead of showing the designed message. The
reader reproduced the `MatchError` against the real changeset.

Fix: match the full return and `Repo.rollback` with the message, as
`TrfImport.create_players/2` does.

### M9 · SWAR import trusts one side's opponent

`swar_import.ex:1776-1806`: `build_round/1` resolves `r.advers` through
`by_ni` with no `opp_r.advers == player.ni` (mutuality) and no `advers !=
player.ni` (self) check; `pair_game/4` then builds a row with the same
player as white and black, inserted via `Repo.insert!` bypassing
`Pairing.changeset/2` (`:1743-1751`). `trf_import.ex:544-556` has exactly
both guards, with a comment saying why.

Fix: the same two guards; treat a failed check as single-sided.

### M10 · SWAR import has no duplicate-NI guard

`trf_import.ex:193` (`validate_unique_ranks/1`) exists because `Map.new`
keeps the last of two equal keys and silently orphans the first player's
games; its comment describes the damage. `swar_import.ex` keys everything
on `p.ni` the same way and has no equivalent (grep: nothing).

Fix: the same pre-flight, before any row is written.

### M11 · A 20-digit FIDE search crashes the search

`fide.ex:15-19`: `~r/^\d+$/` then `String.to_integer/1` (arbitrary
precision) into `Repo.get(FidePlayer, n)` - Exqlite raises `argument
error` on an integer over 64 bits. Callers with no rescue: the players
page (`players_live.ex:421`), the arbiter combo on the public tools page
(`arbiter_combo.ex:99`), and the token-gated `/internal/fide/search` that
OpenResults calls (`fide_lookup_controller.ex:52`). The reader reproduced
it against the database. `Player.max_fide_id/0` (999,999,999) already
exists for the bound.

Fix: parse, then `n in 1..Player.max_fide_id()` or return `[]`.

### M12 · Absence caps above 255 wrap silently in `.swar` export

`swar_export.ex:289-295`: `abs_cap/2` returns the integer unbounded;
`:143` `w_u8/1` is `<<v::8>>`, which masks. `tournament.ex:720-721`
validates only `>= 0`. The sibling `HandyTable` field has an explicit
`@max_handy_table` and a warning; this one has neither.

Fix: `min(cap, 255)` with a logged warning, and an upper bound in the
changeset.

### M13 · The prod listener binds every interface

`config/runtime.exs:375-389`: local mode pins `{127,0,0,1}`; production
binds `::` although the only documented client is `cloudflared` on the
same host. The `/internal/*` bearer routes fail closed without a token,
but the exposure is the whole app on port 4001 to anything the host
firewall lets through - and that firewall is the only control.

Fix: bind loopback by default in production too, with an explicit env var
to widen it. Until then, confirm the Hetzner firewall drops inbound 4001.

### L1 · Actions on mutable tags; write permission on the whole workflow

`elixir.yml:23,26,32`, `binaries.yml:56,58,63,297,309,338`: `@v4`, `@v1`,
`@v2`. `binaries.yml:29-30` grants `contents: write` to all five matrix
jobs on every push to `main`; only the tag-gated release step needs it.
No `pull_request_target` anywhere; `elixir.yml` is `contents: read`; no
secrets are referenced in either file - so the blast radius is a
compromised upstream action writing to this repository from a main-branch
build.

Fix: SHA pins with the version as a comment (Dependabot keeps them
current); a separate release job with the write grant.

### L2 · `redirect_to` filter misses newline

`locale_controller.ex:51`: `@invalid_redirect_chars ["\\", "\t", "%5C",
"%5c", "%09"]`. A decoded LF passes and reaches `put_resp_header`, which
raises `Plug.Conn.InvalidHeaderError` (`deps/plug/lib/plug/conn.ex:272`).
Public route, no auth.

Refuter: **reproduced.** `%0A`, `%0D` and a raw `
` all raise `Plug.Conn.InvalidHeaderError` - neither this filter nor Phoenix's own `validate_local_url/1` strips them.

Fix: an allowlist (`^/[A-Za-z0-9._~/-]*$`) instead of the denylist.

### L3 · `"locked_hint"` converts a param to an atom, no rescue

`settings_options_live.ex:148`, `settings_scoring_live.ex:94`:
`String.to_existing_atom(field)`. The markup only sends known strings; a
crafted event kills the caller's own socket. `admin_live.ex` guards the
same shape and says why.

Refuter: **reproduced** on both pages at the cited lines, and confined to the one socket - a second concurrent mount stayed alive and rendering.

Fix: `when field in ~w(pairing_system …)` guard clause.

### L4 · `set_master` parses an unclamped index

`tools_norms_live.ex:122-127`: `String.to_integer(index)` straight into
assigns; `clamp_master_index/2` (`:216-217`) runs only when files change.
`Combine.combine/2` (`norms/combine.ex:64`) then `Enum.fetch!`s it. Public
page; self-socket crash.

Fix: clamp in `set_master` too, and `Enum.fetch` in `Combine`.

### L5 · Backup restore trusts the file's iteration count

`backup.ex:418-430`: `iterations = crypto["iterations"] ||
@pbkdf2_iterations` from the untrusted header, unbounded, into
`:crypto.pbkdf2_hmac/5`. Reachable only through `mix pairings.backup
restore|verify` today.

Fix: reject outside a sane range.

### L6 · Revoking a phone's enrollment never reaches its socket

`mobile.ex:78-82` sets `revoked_at` and broadcasts nothing;
`mobile_results_live.ex:89-103` keeps reloading the round on every
tournament change without re-checking the enrollment; only `set_result`
(`:141`) does. A revoked phone keeps watching until it tries to write.

Fix: broadcast `{:mobile_enrollment_revoked, id}` on the tournament topic
and redirect in `handle_info`.

### L7 · `open_menu` interpolates raw `x`/`y` into `style`

`pairings_live.ex:276-289` takes `x`/`y` unparsed (the ids beside them go
through `int_or_nil/1`); `:1506` renders `style={"left: #{@menu.x}px; …"}`.
HEEx escapes the attribute, so `;`-separated extra declarations are the
most it allows, on the sender's own socket only.

## Refuted, and kept here on purpose

**"The local-mode auto-login trap is critical behind the tunnel."** Real
mechanism, wrong deployment. `local_owner_session/2` and the loopback pin
are both consequences of `local_mode?`, set from one env var; a box that
has one has the other. What remains is a one-line warning in the local-mode
docs: never put the binary behind a tunnel.

**"`pairings.match_id` is dead schema."** It is in the cast list and the
export deliberately omits it. The *table* is dead; the column is unused
but live.
