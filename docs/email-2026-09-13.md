# Email delivery audit - 2026-09-13

Email delivery was on the 2026-09-05 audit's own list of things nobody had
looked at (`docs/audit-2026-09-05.md`, "What this audit never looked at").
This is that pass, for OpenPairings only - OpenResults sends no mail
(`docs/deployment.md`).

See `docs/email.md` for the operator-facing "how do I set up Gmail SMTP"
guide; this document is the audit, not a replacement for it.

## Every email the app can send

There are exactly four message bodies, all built in one module,
`PairingsEngine.Accounts.UserNotifier` (`lib/pairings_engine/accounts/user_notifier.ex`),
and sent through one mailer, `PairingsEngine.Mailer`. Nothing else in the
codebase calls `Mailer.deliver/1` or `UserNotifier.*` - confirmed by
grepping every caller, not just reading the obvious ones.

| Email | Trigger | Recipient | Subject | Sync/async | Failure handling (now) |
|---|---|---|---|---|---|
| Magic-link login | `UserLive.Login` "Email me a magic link", for an already-confirmed user | The user | "Log in instructions" | Synchronous, in the LiveView process | **[Fixed]** Logged on failure; user sees the same generic flash either way (see Findings #3) |
| Account confirmation | Same trigger, for a not-yet-confirmed user (registration's first email is this one) | The user | "Confirmation instructions" | Synchronous, in the LiveView process | Already handled: `UserLive.Registration.do_register/2` logs and shows a distinct error flash on failure |
| Email-change confirmation | `UserLive.Settings` "Change Email" | The new address | "Update email instructions" | Synchronous, in the LiveView process | **[Fixed]** Logged AND shown to the user on failure (see Findings #3) |
| Collaborator invitation | `Tournaments.add_collaborator/3`, owner invites a co-arbiter by email | The invitee (may not have an account yet) | "You've been invited to `%{tournament}`" | Synchronous, in the LiveView process | **[Fixed]** Correctly reported as `mail_status: :failed` (see Findings #1) |

All four are text-only (`Swoosh.Email.text_body/2`, no `html_body`) - there
is no HTML part to have a plain-text fallback for, and nothing here changes
that. All four are now translated (see Findings #2); previously none were.

Local/desktop mode (`OPENPAIRINGS_LOCAL=1`, or a Burrito build) does not
change any of the above - the same four functions run, the only difference
is which `Swoosh.Adapter` is configured (below).

## Production configuration (`config/runtime.exs`)

| Variable | Read at | Used for | If missing |
|---|---|---|---|
| `SMTP_USERNAME` | boot (runtime.exs:150) and every send (`user_notifier.ex:36`, `deliver/3`) | SMTP auth username AND the From address | See "Adapter selection" below |
| `SMTP_PASSWORD` | boot (runtime.exs:151) | SMTP auth password | Same |
| `PHX_HOST` | boot (runtime.exs:379) | The host in every generated link (magic-link, invite, email-change) | **Silently defaults to `"example.com"`** - see Findings #5 |

### Adapter selection (runtime.exs:150-203)

```
smtp_configured? = SMTP_USERNAME and SMTP_PASSWORD both set and non-blank

cond do
  smtp_configured? and env != :test        -> Swoosh.Adapters.SMTP (Gmail, TLS)
  local_mode?                                -> PairingsEngine.ConsoleMailer
  env == :prod and PHX_SERVER is set         -> raise (refuse to boot)
  true                                        -> leave dev/test adapter as-is
end
```

- **Both credentials present:** `Swoosh.Adapters.SMTP` against
  `smtp.gmail.com:587`, `tls: :always`, `auth: :always`, `ssl: false`
  (STARTTLS), `verify: :verify_peer` with the system's CA bundle and
  `server_name_indication` pinned to `smtp.gmail.com` (runtime.exs:159-174).
  Correctly configured - this is not a plaintext-fallback or
  certificate-skipping setup.
- **Local/desktop mode:** `PairingsEngine.ConsoleMailer` - prints the email
  (and pulls out any links) to the terminal instead of a network call. See
  `console_mailer.ex`'s moduledoc for why this still matters even though
  the local owner is auto-signed-in: a second account on the same machine,
  an invited collaborator, and a password reset all still go through this.
- **Neither credential, in production, with the server actually running**
  (`PHX_SERVER` is what systemd sets - a bare `mix ecto.migrate` does not
  carry it): **boot failure**, with a message naming exactly what to set.
  This is the right failure mode - a confusing crash on the first login
  attempt would be worse - and it is consistent with how `DATABASE_PATH`
  and `SECRET_KEY_BASE` are already handled a few lines below it.
- **Neither credential, dev/test:** untouched - `config/dev.exs` sets
  `Swoosh.Adapters.Local` (preview at `/dev/mailbox`, dev-routes only),
  `config/test.exs` sets `Swoosh.Adapters.Test` (in-memory, what
  `Swoosh.TestAssertions` reads).

**Cross-checked against the deploy script** (`deploy_openpairings.py`, names
only - the file's actual values, and everything under
`openpairings-deploy\.env`, were not read): it reads its OWN `.env` for
`DEPLOY_SMTP_USERNAME` / `DEPLOY_SMTP_PASSWORD` and writes them into the
systemd unit as `Environment="SMTP_USERNAME=..."` /
`Environment="SMTP_PASSWORD=..."` - exactly the names `runtime.exs` reads.
The script also refuses to deploy OpenPairings without them unless
`DEPLOY_SKIP_SMTP=1` is passed deliberately, matching runtime.exs's own
boot refusal. No drift found.

### The from address

`user_notifier.ex:36`: `System.get_env("SMTP_USERNAME") || "contact@example.com"`.
The **only** config-default sending address in source is the placeholder
`contact@example.com` - there is no dedicated OpenPairings sending domain.
In every case where mail is actually delivered over the network,
`smtp_configured?` is true, which means `SMTP_USERNAME` is set, which means
the placeholder is never the address used - it only appears in a
dev/local-preview email that was never going to leave the machine anyway.
The From display name is hardcoded `"OpenPairings"` (not configurable, not
a bug - nothing needs it to be).

## DNS findings

Per the instructions for this audit, this checks the domain that appears in
**config defaults**, not any value in `.env` (never read). That domain is
`example.com`, from the placeholder above.

### `example.com` (the config-default placeholder - not a real sending domain)

| Record | Found |
|---|---|
| MX | `example.com. IN MX 0 .` - a null MX (RFC 7505): explicitly "this domain accepts no mail" |
| SPF (`TXT`) | `v=spf1 -all` - hard fail, i.e. "no server is authorized to send as this domain" |
| DMARC (`_dmarc.example.com` `TXT`) | `v=DMARC1; p=reject; sp=reject; adkim=s; aspf=s` |
| DKIM | Not applicable - no selector, no legitimate sender |

Reassuring, not alarming: IANA has deliberately locked this domain against
mail entirely. If the placeholder ever were used for a real send (it
cannot be, in production - see above), it would bounce loudly rather than
land as convincing-looking spam. There is nothing to add here because there
is nothing this domain is meant to send.

### The real sending domain - operator-configured, not inspected here

Production deliverability rides entirely on whichever account the operator
puts in the secret `SMTP_USERNAME`. `docs/email.md` walks through creating
a Gmail **app password for a personal `@gmail.com` address**, which is the
setup this app is actually documented for. For reference (public records,
looked up here, no operator secret involved):

| Record | `gmail.com` |
|---|---|
| MX | Google's own (`gmail-smtp-in.l.google.com` and four `altN` fallbacks) |
| SPF | `v=spf1 redirect=_spf.google.com` |
| DMARC | `v=DMARC1; p=none; sp=quarantine; rua=mailto:mailauth-reports@google.com` |
| DKIM | Signed by Google's own key on their outbound relay |

**If `SMTP_USERNAME` is a plain personal Gmail address** (the documented
case): nothing to add. Google's own SPF/DKIM/DMARC cover mail sent through
`smtp.gmail.com`, and the app always sets the From address to the exact
same address used to authenticate (`user_notifier.ex:36`), so there is no
from/authenticated-account mismatch for Gmail's relay to reject or rewrite.

**If `SMTP_USERNAME` is ever a Google Workspace address on a custom
domain** instead: that domain's own DNS becomes the operator's
responsibility, and Workspace does not turn all of it on by default -
1. **SPF** - `TXT` at the domain apex: `v=spf1 include:_spf.google.com ~all`
   (Workspace's documented record).
2. **DKIM** - off by default per domain. Enable it in the Workspace admin
   console (Apps > Gmail > Authenticate email), then publish the TXT
   record it generates at `<selector>._domainkey.<domain>` (Workspace
   names the selector, commonly `google`).
3. **DMARC** - Workspace never adds this automatically. Add a `TXT` record
   at `_dmarc.<domain>`, for example:
   `v=DMARC1; p=quarantine; rua=mailto:postmaster@<domain>`
   (start at `p=quarantine`, move to `p=reject` once reports look clean -
   going straight to `reject` on a domain that also sends other mail can
   silently drop it).

Run the same three lookups (`Resolve-DnsName -Type MX|TXT`, and `TXT` on
`_dmarc.<domain>`) against whatever domain `SMTP_USERNAME` actually uses,
and compare against the tables above - this is public information about
your own domain, not a secret.

## Findings, worst first

### 1. [Fixed] A failed collaborator invite was reported to the owner as sent

`Tournaments.deliver_invitation_email/3` (`lib/pairings_engine/tournaments.ex:413`,
called from `add_collaborator/3`) called `UserNotifier.deliver_invitation/4`
and **discarded its return value**, then unconditionally returned `:sent`.
The `rescue` clause around it only catches a raised exception - and
`Mailer.deliver/1` (Swoosh) does not raise on an SMTP failure, it returns
`{:error, reason}`. So the one case the surrounding comment specifically
named ("Never lets a mailer exception (e.g. an SMTP hiccup) crash the
caller") was exactly the case that slipped straight past it. The owner saw
"invitation sent" and had no reason to fall back to sharing
`/invites/<token>` by hand - which `settings_tournament_live.ex:199` was
already written to prompt, correctly, and could never actually reach.

**Fix:** pattern-match the real return value; `:sent` only for `{:ok, _}`,
`:failed` for `{:error, _}`. `rescue` stays as a backstop for anything that
genuinely raises.

**Test:** `test/pairings_engine/tournaments_test.exs`, new test in the
"collaborators" describe block, using a new
`PairingsEngine.FailingMailer` test adapter (`test/support/failing_mailer.ex`)
that makes a send fail without touching the network.

### 2. [Fixed] Every account email was hardcoded English

None of the four templates had a single `gettext` call - not a
process-boundary bug (every send here runs synchronously in the same
LiveView process that already has `Gettext.put_locale/1` set by
`PairingsEngineWeb.Plugs.Locale` / `LocaleHook`, per `docs/i18n.md`), just
never wrapped. A Dutch arbiter's login link, account-confirmation mail,
email-change confirmation, and collaborator invites all rendered in
English regardless of the language their own screen was in.

**Fix:** wrapped all four in `gettext/1,2` (`use Gettext, backend:
PairingsEngineWeb.Gettext`, the same pattern already used in
`features.ex` and `federations/bel/swar_publish.ex`), added the 16 new
Dutch strings to `priv/gettext/nl/LC_MESSAGES/default.po`, checked by the
existing `translations_test.exs`. The three "self" emails (login,
confirmation, email-change) render in the acting user's own locale. The
invitation renders in the **inviting arbiter's** locale - the invitee may
not have an OpenPairings account yet, so there is no other signal, and
`docs/i18n.md` records that no per-user locale is persisted anywhere. This
satisfies "recipient's or arbiter's" locale the same way the rest of the
arbiter UI does.

**Test:** `test/pairings_engine/accounts/user_notifier_test.exs` (new file)
- English and Dutch for all four templates, driven by
`Gettext.put_locale/2` in the test process, asserting the actual rendered
subject and body.

### 3. [Fixed] Two of the four send-result checks were silently discarded

- `UserLive.Login.deliver_magic_link/2` called
  `Accounts.deliver_login_instructions/2` for the resend form and ignored
  the result entirely - no log, no different flash, nothing. A real SMTP
  failure looked identical to a normal send from every angle available to
  the person running the server.
- `UserLive.Settings`'s `"update_email"` handler did the same for
  `Accounts.deliver_user_update_email_instructions/3` - so "A link to
  confirm your email change has been sent" showed even when it was not.

`UserLive.Registration.do_register/2` already handled its own equivalent
call correctly (logs, and shows a distinct error flash) - these two were
the outliers, not the pattern.

**Fix:** both now log the failure
(`Logger.error("Failed to send ... to #{email}: #{inspect(reason)}")`).
The login resend's **flash text is deliberately unchanged** on failure -
it already says the deliberately-vague "If your email is in our system,
you will receive instructions shortly" so as not to leak whether an
address exists, and a different message on failure would reopen exactly
that side channel. The email-change confirmation has no such concern (the
user is already logged into their own account), so it now also shows an
error flash.

**Test:** new cases in `login_test.exs`, `settings_test.exs` and
`registration_test.exs` (the last covers `do_register/2`'s already-correct
branch, which had no test before this), all using
`PairingsEngine.FailingMailer` and `ExUnit.CaptureLog`.

### 4. [Fixed] Local/desktop mode gave no sign that mail was going to a terminal

`UserLive.Login`'s `local_mail_adapter?/0` matched only
`Swoosh.Adapters.Local` (dev's `/dev/mailbox` preview). A local build
(`OPENPAIRINGS_LOCAL=1`, or Burrito) uses `PairingsEngine.ConsoleMailer`
instead - a different adapter - so the check was always false there and
the login page showed no notice at all, even on the paths
`ConsoleMailer`'s own moduledoc says still send mail in that build: a
second account on the same machine, an invited collaborator, a password
reset. Someone on one of those paths clicked "Email me a magic link" and
saw nothing telling them the link had gone to a terminal window instead of
an inbox - and there is no `/dev/mailbox` route in that build either
(`dev_routes` is compile-time false), so the existing notice's link would
have been dead if shown as-is.

**Fix:** `login.ex:359-362` now distinguishes the two adapters and shows an
adapter-appropriate notice - the existing mailbox link for
`Swoosh.Adapters.Local`, a new "printed in this computer's terminal, not
delivered" notice (no link) for `PairingsEngine.ConsoleMailer`.

**Test:** new "mail-adapter notice" describe block in `login_test.exs`,
covering both adapters plus a real-SMTP case (neither notice).

### 5. [Recommended, not changed] `PHX_HOST` silently defaults to `"example.com"` in production

`config/runtime.exs:379`:
`host = System.get_env("PHX_HOST") || (local_mode? && "localhost") || "example.com"`.
Every generated link in the four emails above (magic-link, confirmation,
email-change, invitation) is built from this host via
`PairingsEngineWeb.Endpoint`'s configured `:url`. Unlike `DATABASE_PATH`,
`SECRET_KEY_BASE`, and `SMTP_USERNAME`/`SMTP_PASSWORD` - every one of which
already raises and refuses to boot in production if unset - a missing
`PHX_HOST` does not fail loudly. It silently ships every link pointing at
`https://example.com/...`, a domain the operator does not own, so nobody
who receives one of these four emails could ever act on it. (The same
default also feeds the Keycloak SSO redirect URI, `runtime.exs:255` - a
second, unrelated reason a missing `PHX_HOST` is worse than it looks.)

In practice, `deploy_openpairings.py` prompts for `PHX_HOST` and warns
loudly if it falls back to the SSH host instead, so this requires either
bypassing the deploy script or a hand-run release to actually hit. That is
exactly why this is a recommendation and not a same-pass fix: it is a
boot-time-validation policy question - **since applied, guarded by `PHX_SERVER` like the SMTP check, so build tasks such as `mix ecto.migrate` still run without it** - (should this join the existing
"refuse to boot" group, the same way `SMTP_USERNAME` already does?) that
reaches beyond email into SSO redirect construction, rather than a bug
local to the mailer. Suggested change, for whoever picks this up:

```elixir
host =
  System.get_env("PHX_HOST") ||
    (local_mode? && "localhost") ||
    raise("""
    environment variable PHX_HOST is missing.
    Every link this app emails (login, invitations, email changes) is built
    from it; without it they point at https://example.com, which nobody
    can act on. Set it to the public domain, e.g. openpairings.example.org.
    """)
```
placed alongside the existing `DATABASE_PATH`/`SECRET_KEY_BASE` raises,
guarded the same way (`config_env() == :prod`, but unlike SMTP this one
does not need the `PHX_SERVER` qualifier - migrations don't build links
either way, but nothing bad happens if this raises during a migration-only
run that also happens to lack `PHX_HOST`).

### 6. [Recommended] DNS records for the real sending domain

Covered above under "DNS findings" - add SPF/DKIM/DMARC for the operator's
actual domain if it is ever a Workspace custom domain rather than a
personal Gmail address. Not something this audit can act on directly: the
domain in question is in the secret `SMTP_USERNAME`, never read here.

### Checked, no bug found

- **Token expiry and replay.** Magic-link: 15 minutes
  (`user_token.ex:11`), row deleted on use
  (`accounts.ex:login_user_by_magic_link/1`). Change-email: 7 days, every
  token for that context deleted on use (`accounts.ex:303`). Session: 14
  days. Collaborator invite: token nilled and status flipped away from
  `"pending"` on accept, row deleted on decline
  (`tournaments.ex:accept_invitation/2`, `decline_invitation/2`) - a used
  or declined invite link cannot be replayed.
- **Link host.** Every link is built through
  `PairingsEngineWeb.Endpoint`'s configured `:url` (via `url(~p"...")` or
  `Endpoint.url()`), never a hardcoded host. In production this is
  `[host: PHX_HOST, port: 443, scheme: "https"]` - the PUBLIC port, not
  whatever internal port Bandit actually listens on behind cloudflared -
  so a generated link never leaks the internal port even though the app
  itself only listens on loopback. (Finding #5 above is about `PHX_HOST`
  being wrong when unset, not about how it's used.)
- **Secrets/PII in mail or logs.** Bodies carry only the recipient's own
  email and a one-time token URL - nothing else personal, no secrets. The
  new `Logger.error` lines carry the recipient's email address and
  `inspect(reason)` (an atom or short tuple from Swoosh/gen_smtp, e.g.
  `:timeout` or `{:permanent_failure, ...}`) - enough to diagnose a
  delivery problem, nothing that reaches a full SMTP transcript or a
  password.
- **Plain-text/HTML parts.** All four emails are text-only by design; there
  is no HTML part for a plain-text fallback to be missing.

## Test-send checklist

Run this once, by hand, against a real mailbox - this audit's tests all
use the `Test`/fake adapters and cannot prove real delivery.

1. **Set the environment.** `SMTP_USERNAME` / `SMTP_PASSWORD` to a real
   Gmail address and app password (see `docs/email.md` for how to generate
   one), `PHX_HOST` to the domain you'll actually browse to. Confirm at
   boot that the log does NOT show a ConsoleMailer/Local adapter message
   and does NOT raise about missing SMTP.
2. **Pick a mailbox you can watch** - the Gmail address you're sending
   FROM also works as the recipient for this test (send yourself an
   invite, or register a second account with an address you control).
3. **Trigger one send.** On a fresh instance, the simplest single action is
   **registering a new account** at `/users/register` with that address -
   it both creates the account and sends the first email (confirmation
   instructions) in one step. If the address already has an account,
   `/users/log-in` and "Email me a magic link" sends the equivalent
   magic-link mail instead - but only for an address that already exists,
   by design (see Findings #3), so registering is the one that always
   works on a first try.
4. **In the mailbox, check:**
   - **Subject** matches the table above ("Log in instructions" for an
     existing confirmed account, "Confirmation instructions" for a brand
     new one).
   - **Language** matches the browser/session locale you sent it in - switch
     the language picker to Nederlands first and confirm the subject and
     body come back in Dutch ("Instructies om in te loggen" /
     "Instructies ter bevestiging").
   - **Link host** is the real domain you set `PHX_HOST` to - never
     `localhost`, never a port number, never `example.com`.
   - Click the link once, confirm it works; try the exact same link a
     second time and confirm it is now refused (expired/used).
5. **Open the message's original/raw source** (Gmail: the three-dot menu >
   "Show original") and find the `Authentication-Results` header. Confirm:
   - `spf=pass`
   - `dkim=pass`
   - `dmarc=pass`

   All three passing means the message is authenticated as coming from
   where it claims to; any `fail` or `softfail` there - not a bounce, the
   message arriving but flagged - is the deliverability problem the DNS
   section above exists to prevent, and is diagnosed by which of the three
   failed (SPF failing points at the sending IP/domain mismatch, DKIM
   failing points at a broken or missing signature, DMARC failing means
   the two disagreed with the policy on file).
