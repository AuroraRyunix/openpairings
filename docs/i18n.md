# Languages

English and Dutch. Dutch was completed on 2026-08-29 and is held complete
by `test/pairings_engine_web/translations_test.exs`, which is worth reading
before adding a third language: it enforces the three things about a
catalogue that are decidable, and it exists because "918 of 918" was a true
count and a false conclusion.

Eleven of those 918 were **fuzzy** - gettext's own guesses from `--merge`,
never read by a person - and **Elixir's Gettext uses fuzzy entries at
runtime**, unlike GNU `msgfmt`, which drops them. So they were not gaps
waiting to be filled; they were wrong Dutch on the screen, including two
buttons of one confirmation dialog that read as each other's opposite.

This document otherwise exists because the *scaffolding* is built, so
adding a language is translation work rather than architecture work - and
because the traps below will otherwise be rediscovered the hard way.

## Adding a language

1. Add it to `@locales` in `PairingsEngineWeb.Locale`, as
   `{"nl", "Nederlands"}`. The label is the language's name **in that
   language**: somebody who needs Dutch is looking for "Nederlands" and
   cannot necessarily read the word "Dutch" to find it.
2. `mix gettext.extract --merge`
3. Translate `priv/gettext/nl/LC_MESSAGES/default.po`.
4. Nothing else. The picker appears by itself - it is hidden while there is
   only one language, because a picker offering one option is furniture.

## How a locale is chosen

Session first, then the browser's `accept-language`, then `en`.

The header matters more here than in most apps: the people reading the
public pages are players and spectators with no account and no settings
screen, so the only thing that can speak for them is what their browser
already says. A Belgian visitor asking for `nl-BE` gets Dutch the day Dutch
exists, without touching anything.

Region subtags collapse: `nl-BE`, `nl-NL` and `nl` all resolve to `nl`.
Chess vocabulary does not differ between Flanders and the Netherlands
enough to justify two catalogues.

## The two traps

**A LiveView does not run in the process that served the request.**
`Gettext.put_locale/1` is per-process, so the plug alone reaches the dead
render and nothing after it: the page would render translated, connect, and
silently re-render in English. That is why `PairingsEngineWeb.LocaleHook`
exists and why it is listed on **every** `live_session`. `locale_test.exs`
walks the router and fails if one is missing, because the symptom - one
page in the wrong language - is invisible to anyone testing in English.

**The plug writes the resolved locale back into the session.** Without
that, a visitor whose language came from the header would have nothing
stored, and the LiveView mounting a moment later cannot see headers. The
dead render and the live render would disagree, which looks like the page
changing language as it loads.

## What is wrapped, and what is deliberately not

**Wrapped: the arbiter UI.** 1418 messages as of 2026-09-12, across the
settings screens, pairings, players, standings, norms, history, the login
pages and every printed document.
`priv/gettext/<code>/LC_MESSAGES/default.po` is the one file per language -
one entry per string, with the source file and line recorded against each so
a translator has context.

Do not read that number as coverage. The audit of 2026-09-12
(`docs/translations-audit-2026-09-12.md`) found whole surfaces still outside
it - the Audit page's own sentences, the tie-break descriptions, the Print
page's document list, every flash in the session controllers - because they
are built by interpolation or held in module attributes, which is the same
shape of blind spot `PrintController` was.

**Pinned to English: the player-facing pages.** Mobile result entry renders
in English whatever locale is chosen, via `PairingsEngineWeb.EnglishHook`.
The public tournament pages were on this list until 2026-08-29; they now live
in OpenResults, which answers the same question for itself.

That is a decision, not an omission. An open draws players from a dozen
federations, and the language a Belgian arbiter picked for their own admin
screens is not a sensible thing to impose on a Polish player reading the
standings. English is what that room mostly shares. The arbiter UI is the
opposite case: one person, usually local, running the event.

If that is ever revisited, remove `EnglishHook` from those sessions in the
router - do not go hunting for missing `gettext` calls, because they were
never the cause.

**The pin has a hole in it.** `EnglishHook` is a `live_session` hook, and
the phone's first page is not a LiveView: `MobileEnrollController` serves
`/m`, `/m/e/:token` and `/m/leave` through the `:browser` pipeline, where
`Plugs.Locale` has already resolved the arbiter's language. Its template
(`mobile_enroll_html.ex`) is unwrapped English while its five error lines
ARE wrapped and translated, so a Dutch session gets the heading, blurb,
field label and button in English and the error in Dutch, on one card - and
then `/m/results` in English again. Pick a side: either drop `gettext` from
those five call sites, or pin the `/m` scope's locale in the pipeline the
way the hook pins the session. `locale_test.exs` only walks
`live_session`s, which is why it does not see this.

Never translated at all: FIDE report forms (IT3/FA1/IA1 are FIDE's own
English documents), TRF field names, engine names, and audit action codes.
Those are identifiers, not prose.

## A trap in the wrapping itself

HEEx escapes the output of `gettext/1`, so an HTML entity left inside a
msgid gets escaped a SECOND time: `"Norms &amp; FIDE reports"` renders as
`Norms &amp;amp; FIDE reports`. Msgids therefore hold the real character -
`&`, `·`, `→` - and HEEx escapes it correctly on the way out. Anything
carrying a literal double quote uses `~s()` rather than `"`.

**`%%` is not an escape here.** `Gettext.Interpolation.Default` replaces
`%{name}` and touches nothing else, so a doubled percent sign is not undone
the way it is in a printf format or a GNU `c-format` string - it reaches the
screen as two characters. Two strings on Settings > Options were written on
that assumption and shipped reading "roughly 4%% of rounds" - in English as
well as in Dutch, since the msgid renders directly for the source locale.
Write a single `%`. `translations_test.exs` refuses `%%` now, in the
templates as well as the catalogues.

**Leave the `en` msgstrs empty.** English renders from the msgid; a filled
`en` msgstr is a second copy of the source text that nothing keeps in step,
so the next reword leaves it behind and English readers keep seeing the old
wording. One had already happened. Also refused by `translations_test.exs`.

## Not built

Per-user and per-tournament persistence. The choice lives in the session,
so it follows a browser rather than an account, and a club cannot yet pin
its public pages to one language regardless of visitor. Both are additive:
a `users.locale` column and a `tournaments.public_locale` column feeding
`Locale.resolve/2` ahead of the header.

## A sentence that wraps around something

A sentence that wraps around an inline value - a link, a name, a round
number - cannot be a single `gettext/1` call as written. Splitting it in
two produces a fragment, and a fragment is worse than leaving it English:
the page renders half in each language, and a translator handed
`"to set it for everyone at once."` on its own has nowhere to put it,
because Dutch does not order a clause the way English does. That is
exactly what the first wrapping pass did to the Players page.

**Never wrap a fragment to raise the count.** The count is not the goal.

Around a plain VALUE, use an ordinary gettext binding:

```heex
{gettext("Rounds are paired in order - round %{n} is next.", n: @next_round)}
```

Around MARKUP - a link, a `<strong>`, a `<code>` - use
`CoreComponents.rich_text/1`. The whole sentence stays one msgid; the
placeholder is where the markup goes, and the translator is free to move it:

```heex
<.rich_text text={gettext("Players get their category on the %[players] page.")}>
  <:part name="players">
    <.link navigate={~p"/t/#{@tournament.id}/players"}>{gettext("Players")}</.link>
  </:part>
</.rich_text>
```

Square brackets, not gettext's own `%{...}`, and this is not cosmetic:
gettext interpolates `%{...}` itself, and a msgid carrying one with no
matching binding logs `missing Gettext bindings` at :error on **every
render**. `%[...]` is for `rich_text` to fill; `%{...}` in the same sentence
still means an ordinary binding. `rich_text_test.exs` pins both, including
that no whitespace creeps in around the substitution.

## The other trap: HTML built as strings

`PairingsEngineWeb.PrintController` assembles its documents by string
concatenation, not HEEx. Every gettext pass that walked `~H` blocks
therefore skipped it completely, and pairing sheets, standings, place cards
and player lists printed in English no matter what the arbiter had chosen.
It stayed that way for two whole passes because nothing in the extraction
output looked wrong - the strings simply were not there to be counted.

Two rules apply there and not elsewhere:

* **Entities are not double-escaped.** The output is interpolated raw, so
  `&middot;` in a msgid renders as `·` rather than as the literal text.
  Msgids still hold the real character, for one spelling per string.
* **Escape the values, not the msgid.** Data still goes through `esc/1`
  before it becomes a `%{}` binding; the catalogue itself is authored and
  shipped in-repo, and carries no markup.

`locale_test.exs` asserts a printed document comes out in Dutch, separately
from the LiveView assertion - it is a different process path, and only the
print test would have caught this.

## What is still English, and why

Codes. Column headers that are abbreviations (`Pr.`, `Nr`, `Fed`, `Id Nat`,
`Elo`, `Pts`, `Rd`, `N-Elo`, `Res`, `Cl`, `Flt`, `XtPts`, `feds`, `host`),
FIDE's own symbols (`We`, `W-We`), result notation (`1-0`, `W`, `B`), FIDE
form names, file extensions, and `bye` / `tiebreak` / `Elo`, which
Dutch-speaking arbiters say in English anyway. The on-screen Players grid
and the printed player list are meant to share those labels one-for-one, so
translating one and not the other would be worse than translating neither.

They do not actually share all of them. The grid says `Country` / `Elo Nat`
/ `Elo FIDE` where the printed list says `Fed` / `Nat.` / `FIDE`, and both
sides are unwrapped literals in a module attribute, so the *effect* holds
(English on both) while the premise does not. Check rather than assume if
you touch either list - `players_live.ex`'s `@columns_before_tiebreaks` and
`print_controller.ex`'s `@player_list_columns`.

Some of those codes ARE in the catalogue, wrapped, with a Dutch msgstr
identical to the msgid - `N-Elo`, `Elo`, `bye`, `Cl.`, `#Ptn`, `W-We`. That
is the convention, not an oversight: it keeps the string in one place, and a
future language that does spell a code differently has somewhere to say so.
The failure mode is the opposite one, and it has happened: `W-We` was
translated to `W-Wv`, next to a `We` header that is a bare literal, so two
adjacent columns spelled the same symbol two ways.

Product and personal names are never in the catalogue: `OpenPairings`,
`Ainalrami`, `JaVaFo`, `SWAR`, and the name in the credit line. The brand
mark is `Open<strong>Pairings</strong>` - two elements for styling, one
name. An automated pass wrapped the `Pairings` half of it once, which would
have rendered the product as "OpenParingen" the moment somebody picked
Dutch.

The credit line is the exception, and an unintended one: the About tab keeps
the name out with a `%[who]` part (`settings_about_live.ex`), while the
printed footer has it inside the msgid
(`print_controller.ex`, "Paired by OpenPairings using %{engine} · many
thanks to …"). Two surfaces, one name, two treatments. The `%[who]` one is
the shape to copy.
